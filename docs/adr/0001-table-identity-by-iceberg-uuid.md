# 1. Table identity by Iceberg table UUID

Date: 2026-10-24

Status: Accepted

## Context

The table maintenance control plane keeps a registry of managed tables, their settings and their maintenance history. Tables can be renamed, dropped and recreated under the same name. History must stay attached to the table it belongs to, and registry rows are never deleted.

Every Iceberg table carries a `table-uuid` in its metadata. It is assigned at creation and survives renames. A table that is dropped and recreated with the same name gets a new UUID.

## Considered options

1. Identify a table by its name (`catalog`, `namespace`, `table`).
2. Identify a table by a surrogate key generated by the control plane, with the name as a unique key.
3. Identify a table by its Iceberg `table-uuid`, with the name as a mutable attribute.

## Decision

Option 3. `ManagedTable` uses `TableUuid` (the Iceberg `table-uuid`) as its identity. `TableName` is an attribute that a rename updates in place. A table that is gone from the catalog is marked `DROPPED`, not deleted. A table recreated under the same name is a new row with a new UUID. The table reconcile workflow ID is derived from the UUID (`table-reconcile-{uuid}`).

## Consequences

- Renames keep settings, operation state and run history. Discovery and the event consumer detect a rename when they see a known UUID under a new name.
- Drop and recreate never mixes the history of two different tables.
- Name-based lookups (event hints carry names, not UUIDs) need a catalog read first to resolve the UUID. That read is also what makes the catalog the source of truth (ADR 3).
- A stale row can share its name with a new table. Name lookups must expect this, and discovery reconciles the stale row (marks it `DROPPED`) when it sees a new UUID under a known name.
- Tables imported or registered from existing metadata (`register_table`) keep the UUID from that metadata. Two catalog entries that point to the same metadata would collide; this is not supported.
