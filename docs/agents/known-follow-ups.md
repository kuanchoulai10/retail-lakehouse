- Compaction candidates (2026-11-13, milestone 3): observation still reads every manifest entry of the table on each scheduled reconcile, so large tables are slow to observe and the worker's memory grows with the file count. An incremental path needs a stored per-partition statistics state kept in step with the snapshots (the compaction verdict, the delete-file checks and health sum over every partition), and PyIceberg 0.11 cannot write the replace snapshots and delete files its tests need (KCL-53). The lost-update window between candidate writers is closed (milestone 4): rows carry a `version` and `save_all` refuses the whole save when any row moved (`StaleCompactionCandidate`, retried by Temporal). A record step that fails for good can still leave a partition waiting out its claim lease (about 20 hours), never a lost compaction, since the next observation decides. A plan also releases claims of runs with no run record and of finished runs, looking each holder up. The quiet period trusts snapshot commit times and leaves out compaction's own (`replace`) snapshots; a writer that commits as `replace` would never count as writing. The throughput estimate assumes bytes rewritten per hour scales with the bytes picked; it is `rewritten_bytes_count` over the succeeded attempt's duration for the newest 10 compactions, that duration includes Spark start-up and the jar downloads, so compactions below `GLAC_COMPACTION__MIN_THROUGHPUT_SAMPLE_BYTES` (64 MiB) are left out and a table with only small ones uses the default. - Compaction rounds (2026-11-13, milestone 4 and its fix rounds 1 and 2; fix round 1 deployed from `dfe0e076`, fix round 2 from `c71b2cf2`): wave 21's `bootstrap.sh` must register `GrantedTableUuids` before the wave-25 worker starts; the worker now checks every search attribute it sets at start and refuses to start, naming the script, when one is missing. Spark names the driver Service `<app name>-<hex>-driver-svc`, which is now over 63 characters, so Spark always falls back to a generated name and logs a warning; nothing reads that name. `CompactionCandidate.granted_round_id` and `RecordedAttempt.run_id` are plain strings (typed ids would cause an import cycle); the second is shape-checked. `TableMaintenancePolicyName`'s "not shaped like an id" rule copies the pattern of `shared_kernel.prefixed_id_pattern` by hand. The attachments repo's `get_many(ids)` is now used only by tests. The candidates repo turns every `IntegrityError` into `StaleCompactionCandidate`, so a non-unique integrity bug would retry forever. A discovery rule sent with `"id": ""` is treated as new and then refused with a confusing "unknown rule id" naming an id the client never sent.

- Each Volcano queue's capability (cpu 2, 5017Mi) is one L job and is not derived from `spark.sizes.L` (KCL-92); raising L's memory in values makes every L PodGroup exceed the queue and wait until its attempt deadline. Because every size needs 2 CPU, a queue runs one job of any size at a time; raise `capability.cpu` to let memory decide concurrency.

- Maintenance workflow history (2026-11-20, KCL-93): `TableMaintenanceWorkflow` never continues-as-new, so one run's history grows with every status poll (about 11 events each). A queued attempt polls every 30 s for 10 minutes, then every 10 minutes; a running one every 30 s for 10 minutes from its driver start, then every 5 minutes. Measured on the time-skipping server: an attempt queued out at the 24 h limit takes 162 polls and 1,836 events, and one operation whose three attempts each wait about 24 h and then run out the 6 h deadline and fence takes 5,478 events. A run of all four operations at that worst case comes to about 22,000 events: under Temporal's 51,200-event limit, but past its 10,240-event warning. A longer queue wait limit or deadline, more attempts or more operations raises that; continue-as-new between operations, or a slower poll, would bound it.
- Time-skipping test server and continue-as-new (2026-11-20, KCL-93): once `TableReconciliationWorkflow` has continued-as-new, any close of the maintenance child that its previous run started stops the test server's clock. The close may be a give-up cancel (the child reports back and the next run starts correctly) or a plain `complete`. The next `env.sleep` then fails with `RPCError: Timeout expired` after 30 s of real time, with no pending activity, workflow task or child task, and only a timer outstanding. Without continue-as-new the same close does not stop the clock. To reproduce, in `test_table_reconciliation_workflow.py`: `h.start(continue_as_new_after=2)`, wait for `h.in_flight()`, send three `POLICY_CHANGED` signals, wait for a new Temporal run id, `h.complete_child(run_id)`, `h.plan_count(2)`, then `h.env.sleep(timedelta(minutes=5))`. It looks like a test-server problem: a closed child report to a parent run that has continued-as-new (ABANDON) does not release time skipping; this was not checked on a real server. The workflow tests therefore cover continue-as-new give-ups only with a carried run that has no live child.
