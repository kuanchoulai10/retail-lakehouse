- Maintenance workflow history (2026-11-20, KCL-93): `TableMaintenanceWorkflow` never continues-as-new, so one run's history grows with every status poll (about 11 events each). A queued attempt polls every 30 s for 10 minutes, then every 10 minutes; a running one every 30 s for 10 minutes from its driver start, then every 5 minutes. Measured on the time-skipping server: an attempt queued out at the 24 h limit takes 162 polls and 1,836 events (one poll, about 11 events, more since the poll at the limit was added), and one operation whose three attempts each wait about 24 h and then run out the 6 h deadline and fence takes 5,478 events. - Time-skipping test server and continue-as-new (2026-11-20, KCL-93): once `TableReconciliationWorkflow` has continued-as-new, any close of the maintenance child that its previous run started stops the test server's clock. The next `env.sleep` then fails with `RPCError: Timeout expired` after 30 s of real time, with no pending activity, workflow task or child task, and only a timer outstanding. Without continue-as-new the same close does not stop the clock. To reproduce, in `test_table_reconciliation_workflow.py`: `h.start(continue_as_new_after=2)`, wait for `h.in_flight()`, send three `POLICY_CHANGED` signals, wait for a new Temporal run id, `h.complete_child(run_id)`, `h.plan_count(2)`, then `h.env.sleep(timedelta(minutes=5))`. It looks like a test-server problem: a closed child report to a parent run that has continued-as-new (ABANDON) does not release time skipping; this was not checked on a real server. The workflow tests therefore cover continue-as-new give-ups only with a carried run that has no live child.
