# Known Follow-ups

Open issues and deferred work. Not loaded automatically; read the entries for the area you are about to change. Remove an entry when it is fixed.

- Login gate trust boundaries (`13-identity` README): client-sent `X-Auth-Request-*` reach upstreams on ungated paths and when oauth2-proxy omits a claim (strip at the gateway before any upstream trusts them; phase-3 precondition); `--trusted-proxy-ip` unset with `x-forwarded-host` in the check headers lets a client steer its post-login redirect host; `KC_PROXY_HEADERS=xforwarded` trusts in-cluster callers; any route under `/sso`, `/keycloak` or `/polaris` is ungated.
- `platform/21-polaris/bootstrap.sh` creates the `polaris-token-broker` Secret with a check that treats any `kubectl get` error (not just NotFound) as missing and uses `apply`, so a transient API error could regenerate the key pair. Make it NotFound-only plus `kubectl create` (as `25-lakehouse-control-plane/bootstrap.sh` does for `table-maintenance-db`).
- Worker and event-consumer pods have no liveness probes (deferred).
- Table maintenance control plane (wave 25): the migrate Job reruns on every `helm upgrade` (name carries the release revision); `helm upgrade --wait-for-jobs` waits for it and `validate.sh` asserts the current-revision Job completed; api / worker / event-consumer also gate on the seeded `default` table maintenance preset. The e2e tables `iceberg.e2e.tm_e2e_orders` / `tm_e2e_regions` and the rule `include iceberg / e2e / tm_e2e_*` stay in place (removal steps in the wave README).
- Node memory pressure (eased 2026-10-24, 2026-11-01 and 2026-11-03): on 2026-10-24 Trino got memory limits (coordinator `-Xmx2G` / 2816Mi, worker `-Xmx3G` / 4Gi, jmx-exporter 384Mi) and KEDA scales workers 1 → 2 (max 2, 2 running queries per worker), so Trino uses ~5.3 GiB at 1 worker (was ~8 GiB idle and unbounded under load) and the node dropped from 75% to 64%. The earlier `<unknown>` HPA metric was not a KEDA misconfiguration: under memory pressure `prometheus-k8s-0` and `keda-operator-metrics-apiserver` restarted, and while the metric is unknown the HPA keeps its replica count. On 2026-11-01 the remaining unbounded pods got memory request / limit: Kafka brokers 1536Mi / 2560Mi with heap `-Xms1g -Xmx1g` (were unbounded, 3.7 / 3.4 / 1.9 GiB), iceberg-connect 896Mi / 1Gi and debezium-connect 640Mi / 1Gi (heap 512m), RustFS 832Mi / 3072Mi (was 1630 MiB), Jaeger 256Mi / 512Mi with `max_traces: 20000`. Requests are sized from usage, not set equal to the limits: with request = limit, running pods requested 27013Mi of 28005Mi allocatable, so a Spark maintenance driver fit but its executor (1433Mi) did not and `e2e.sh` stalled; the deployed configuration requests 20396Mi (72%), room for two concurrent driver + executor pairs. RustFS's limit was first 2176Mi; it was OOMKilled once at that limit under the e2e load and the next run peaked at 2316 MiB, so the limit is that peak plus about 30%. Measured on the deployed configuration after a clean onboard, an `e2e.sh` run and a 30 minute soak with no changes (14:05–14:35): node 61% (17222Mi), brokers 675 / 751 / 678 MiB, iceberg-connect 739 MiB, debezium-connect 452 MiB, RustFS 1527 MiB (2316 MiB right after the e2e), Jaeger 393 MiB, no OOMKilled and no rise in restart count for any bounded pod (an earlier 58% figure was a cold-cache floor). RustFS and Jaeger settled above their requests after load, and the Trino worker was OOMKilled at its 4Gi limit during the e2e INSERT burst (twice on 2026-11-01; a container OOMKill, not a Java heap OOM: the 3G heap left ~1 GiB for non-heap memory). On 2026-11-03 the RustFS request went to 1638Mi and Jaeger's to 448Mi (limits unchanged), and the worker limit to 5Gi with the request kept at 4Gi and the heap and query memory unchanged. Measured after a clean onboard, two `e2e.sh` runs and a 30 minute soak (00:44–01:14): Trino worker peak 4155 / 4331 MiB in the two e2e runs (cgroup `memory.current`, above the old 4096 MiB limit), no OOMKill; node 58% (16484Mi), 21394Mi of 28005Mi requested (76%, +998Mi), brokers 695 / 776 / 747 MiB, iceberg-connect 776 MiB, debezium-connect 412 MiB, RustFS 1224 MiB (peak 1666), Jaeger 285 MiB, Trino coordinator 1881 MiB (peak 1907), worker 2558 MiB; no OOMKilled and no restarts in any Running pod. Concurrent Spark maintenance jobs under load were not re-tested. On 2026-11-06 wave `13-identity` added 704Mi of requests (Keycloak 640Mi); 22130Mi of 28005Mi is requested (79%, with the out-of-repo Polaris console spike's 32Mi) and two driver + executor pairs leave only about 140Mi, so the next new workload needs room made elsewhere.
- Spark result callback retries only 3 times 5 s apart (`runtime/spark/result_callback.py`); across a DB / Temporal outage the run is recorded from the polling fallback as `{"completed_without_callback": 1}` and the procedure metrics are lost. Widen the retry window or have the poller read the result from the driver.
- `rewrite_data_files` runs with `partial-progress.enabled=true`; the runtime now fails a CALL with failed and zero rewritten data files, but a lost callback still records success from the poller (`completed_without_callback`).
- Each SparkApplication downloads the Iceberg, `hadoop-aws` and `s3-transfer-manager` jars from Maven Central at submit; bake them into `table-maintenance-spark`.
- Spark event logs: no consumer of `spark-event-log-completions` exists yet. A driver that crashes or is killed never renames its `.inprogress` marker, so it sends no completion event (its log still expires after 3 days). RustFS accepts a bucket notification naming an unregistered target ARN with only a warning, so `20-rustfs/validate.sh` proves the saved config, not that the target is live. Message keys / `s3.object.key` are URL-encoded and `awsRegion` is empty; delivery is at least once.
- Event-driven runs with the `default` preset start while a writer is still committing; the 10-min discovery fallback was not exercised by the e2e (the event path found the tables first). On a fresh cluster the e2e tables do not exist at its pause step, so the default preset compacts them mid-write and the manual compaction can then rewrite fewer than 20 files: `e2e.sh` failed its reclaimed check once on 2026-11-03 (18 < 20) and the rerun passed.
- `Table` (formerly `ManagedTable`) updates can be lost under concurrent writers: add a version column with compare-and-set.
- A retried `record_maintenance_operation_result` activity can lose the table's backoff update.
- The discovery enabled switch and the `table-discovery` schedule can drift until the worker restarts.
- Every CDC commit sends a hint that triggers a full metadata scan in the plan; debounce planning.
- No auth on the API or the Spark result callback, and no NetworkPolicy.
- Table maintenance uses the Polaris root principal; switch to a scoped principal.
- The SparkApplications the backend submits (`spark_application_manifest.py`) carry no `app.kubernetes.io/*` labels; the label standard covers only `platform/` manifests and the wave-25 chart.
- The running `table-maintenance-admission` workflow keeps the limit and lease it was started with; a changed `GLAC_ADMISSION_LIMIT` or lease applies only after it is restarted while idle.
- Catalog-wide sync re-ensures every live table's reconciliation workflow each run: one Temporal error aborts the rest of the sync (catch per table), and each wake costs a metadata scan (add start-without-signal).
- `TableReconciliationWorkflow` give-up changes have no `workflow.patched` guard; a history holding an old-code give-up would hit nondeterminism on replay. The give-up budget ignores admission-queue wait time.
- On-hold waves still reference pre-rename names (`minio-api.minio.svc`, `kafka-cdc`, `polaris`, `platform/20-minio`): `30-thanos`, `24-e2e-validation`, `charts/app-of-apps`. Fix when those are re-opened.
- Iceberg sink (Kafka 4.0 + sink 1.10) may commit "0 table(s)" for several minutes after a Connect pod start under low traffic; keep inserting and poll ~5–10 min when verifying snapshots.
- `bitnami/jmx-exporter` (Trino sidecar) is pinned by digest: Bitnami's free catalog only publishes `latest`, so bumping it means taking the new `latest` digest.
- NetworkPolicies are not enforced (bridge CNI). kube-prometheus and Strimzi ship policies that would block KEDA → `prometheus-k8s` and Kafka UI → Connect REST (:8083); before moving to an enforcing CNI (kindnet, Cilium, Calico), add allow rules for those paths. The Kiali chart also creates a NetworkPolicy; Kiali needs gateway → Kiali (:20001) and Kiali → Prometheus allow rules before an enforcing CNI is used.
- Keycloak realm edits on a running cluster are manual: `--import-realm` skips an existing realm, so a changed `keycloak-realm-configmap.yaml` or public origin needs the admin console / `kcadm.sh` or a re-onboard.
- Rotating Keycloak's `trino` client secret needs a `23-trino` bootstrap rerun (it copies `trino-client-secret` into `trino-credentials`).
- Trino's `checksum/trino-env` pod annotation comes from a Helm `lookup`, so it is constant under `helm template` (ArgoCD path, on hold) and a secret change would not restart the pods there.
- oauth2-proxy runs without session refresh: a disabled or deleted Keycloak user keeps gateway access until the 12h cookie expires.
- oauth2-proxy answers `/robots.txt` at the root before auth, so the gate would pass it; it is DENY-listed by `platform-gateway-sso-builtins`. A new root-level handler in an oauth2-proxy upgrade needs another DENY entry (and a `13-identity/validate.sh` probe).
- Single sign-on phase 3: Polaris (its own principals and tokens, `/polaris` ungated) and workload identities (services, Spark jobs) do not use Keycloak yet.
- The containerd registry `hosts.toml` is keyed on the registry ClusterIP and written only by `task cluster:bootstrap`; if the `registry` Service is ever recreated, re-run `task cluster:configure-registry-mirror KUBE_CONTEXT=...`.
- Backend architecture tests with more than one context: `test_every_aggregate_has_a_repository_port` (`tests/architecture/test_import_boundary.py`) asserts a global `>= 5`; compare each context's repository ports with `aggregates(context)` instead. Three checks also expect every context to have the table maintenance adapter shape: `test_directory_structure.py` (`ADAPTER_SUBDIRECTORIES`: web, event_consumer and temporal adapter directories), `test_temporal_workflow_determinism.py::test_workflow_modules_are_found` (at least one Temporal workflow) and `test_aggregate_axis.py::test_hybrid_outbound_dirs_are_found` (an `adapter/hybrid/temporal/outbound` directory); the project that adds the second context decides whether they become "only if present".
