- Spark result callback retries only 3 times 5 s apart (`runtime/spark/result_callback.py`); across a DB / Temporal outage the run is recorded from the polling fallback as `{"completed_without_callback": 1}` and the procedure metrics are lost. - `rewrite_data_files` runs with `partial-progress.enabled=true`; the runtime now fails a CALL with failed and zero rewritten data files, but a lost callback still records success from the poller (`completed_without_callback`). Partial progress also drops a commit silently (seen 2026-11-24 by the e2e `test_partition_cap_and_order.py`): it commits each file group on its own from the rewrite threads at once, the commits conflict with each other in Polaris ("concurrently modified"), one runs out of retries, and Iceberg logs "Failure during rewrite commit process, partial progress enabled. Ignoring"; the procedure returns without counting it (`failed_data_files_count` 0), so the run reads `succeeded` while a selected partition kept every file, until the next check selects it again. Options: raise `commit.retry.num-retries` on the call, lower `max-concurrent-file-group-rewrites`, or compare the rewritten groups with the selected partitions and record the gap. The scenario turns partial progress off in its own policy.

- Maintenance workflow history (2026-11-20, KCL-93): `TableMaintenanceWorkflow` never continues-as-new, so one run's history grows with every status poll (about 11 events each).
