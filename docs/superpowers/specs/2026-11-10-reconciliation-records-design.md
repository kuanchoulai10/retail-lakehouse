# Reconciliation records and dry run

Status: draft, 2026-11-10. First of four specs that redesign table-maintenance reconciliation.

## Why

**Today a reconciliation decides and forgets.** Every table has one `TableReconciliationWorkflow`. It wakes on its timer, on a catalog commit, or on a settings, pause, resume or manual-run signal, and calls `plan_table_maintenance`. That activity runs `assess_maintenance`, which works out for each of the four operations whether it is due, cooling down, disabled or not needed, together with the measured value and the threshold. Only the resulting run is stored. When maintenance did nothing, or did something unexpected, the console cannot say why.

The user wants each reconciliation kept and shown: what woke it, what it measured for each operation, whether a threshold was crossed, what it started, and a link to the run it started. That is the first deliverable of the redesign, and it comes before any change to the rules. It also makes the later specs observable: new conditions, triggers and per-operation workflows will show up in the same record.

**Dry run belongs in this spec** because it is the same thing with one change: reconcile and record as usual, but start nothing. It lets the user try settings on a table, or a preset on many tables, and see what would happen.

## The four specs

Agreed order. Each spec gets its own plan.

1. **Reconciliation records and dry run** (this spec).
2. Per-operation conditions: each operation gets a fixed set of three or four metrics that can be combined with AND or OR, each with its own threshold. Compaction also skips partitions that were written recently; pyiceberg's partitions metadata carries a last-updated time.
3. Reconciliation triggers: interval, cron, catalog commit, commit count and full-scan interval, plus a configurable debounce.
4. One Temporal workflow per operation, run one at a time per table, with a default queue order and no hard dependency between operations.

These stay as they are: the per-operation cooldown (`min_interval` with failure backoff) and the one-run-at-a-time rule.

Deferred to no spec yet: maintenance windows, budget caps, approval, adaptive evaluation and policy inheritance.

## Goals

- Every reconciliation that reaches a decision is stored as one record and shown in the console.
- A record reads without code knowledge: why it woke, a one-line outcome, and per operation a status and a one-sentence reason.
- The full measurements are one click away, never in the way.
- A table, or a preset, can be put in dry run. Its reconciliations record "would start" and start nothing.
- A user can ask for a reconciliation right now ("Reconcile now"), separately from "Run now".

## Non-goals

- No change to when a table is reconciled or to which operations are judged due. That is specs 2 and 3.
- No run detail page; the run link opens the existing Maintenance tab at that run.
- No cross-table view of reconciliations.

## Anti-goals

- **The history must not become a wall of data.** The user rejected a first mockup that expanded every reconciliation into a table of metrics. Hourly reconciliations that do nothing must not drown the ones that did something.
- No "detection / decision / execution" vocabulary in the UI or the model. The word is **reconciliation**, matching `TableReconciliationWorkflow`.

## Vocabulary

- **Reconciliation**: one pass in which the reconciliation workflow looks at a table and decides. The UI says "Reconciliations", "Reconcile now" and "Reconciled by schedule at 10:42". The domain aggregate is `TableReconciliation`, named like `TableMaintenanceRun`.
- **Wake reason**: what woke the workflow. One reconciliation can have several, because signals that arrive while a run is in flight, or before the loop gets to plan, are coalesced.
- **Operation outcome**: what the reconciliation concluded for one operation.

## The record

A `TableReconciliation` aggregate in the table-maintenance context, stored in its own SQL table. One record per call of the plan activity that finds the table's maintenance row. A missing row (reported today as `dropped`) stores nothing, since the table has left maintenance and its records go with it. A plan activity that fails before deciding stores nothing; the workflow already logs that.

Fields:

| Field | Meaning |
|---|---|
| `id` | Generated by the workflow, so the record and the run can point at each other. |
| `table_uuid` | The table. |
| `reconciled_at` | The `now` the workflow passed in. |
| `wake_reasons` | Each distinct reason with a count, e.g. catalog commit × 3. See below. |
| `dry_run` | Whether the table was in dry run at the time. |
| `outcome` | `planned` or `skipped`, plus the skip reason (`paused`, `dropped`, `excluded`, `not_found`). `dropped` here means the row says dropped; a missing row stores no record. |
| `operations` | For a planned reconciliation, one entry per operation in the default order; empty for a skip. |
| `run_id` | The run it started, if any. |

Each operation entry holds:

- `operation`;
- `result`: one of
  - `started`;
  - `would_start` (dry run);
  - `not_needed`;
  - `start_failed` (due, but the run could not be started);
  - `cooling_down`, with `next_eligible_at`;
  - `off` (disabled in settings);
  - `not_checked` (a manual run that did not name it);
- `combine`: `all` or `any`;
- `measurements`: a list of `{key, observed, unit, threshold, comparison, met}`. `observed` and `threshold` are numbers in the stated unit (count, bytes or seconds), so the console formats them. **A measurement that only gives context has no threshold:** `threshold`, `comparison` and `met` are null, it never decides the outcome, and the reason sentence leaves it out. "All measurements" lists it without a met mark.

A manual run ("Run now") is not assessed. The operations it names are recorded as `started` with no measurements, the rest as `not_checked`, and the wake reason `manual_run` is what tells it apart. Its `dry_run` field records the setting as it was, and the console shows "Started … (manual run, dry run is on)" so the two do not read as a contradiction.

Today every operation has at most one deciding measurement:

| Operation | Measurement |
|---|---|
| Compaction | Reducible files (decides). The target file size and, in partition scope, the qualifying partitions are context measurements. |
| Manifests | Small manifests. |
| Expire snapshots | Expirable snapshots, threshold 1. |
| Orphan files | None; it is due whenever its cooldown allows. |

Spec 2 adds measurements and real `any`/`all` combinations without changing the record's shape. That is why the shape is a list from the start.

**The reason sentence is not stored.** The console builds it from the structured fields, so wording can change without a migration.

### Wake reasons

The workflow tracks why it woke instead of a single `_woken` flag.

| Reason | Source |
|---|---|
| `schedule` | The timer. |
| `catalog_commit` | `table_updated`. |
| `settings_changed` | Settings signal. |
| `resumed` | Resume signal. |
| `paused` | Pause signal. |
| `manual_run` | `trigger_now`. |
| `reconcile_now` | New signal. |
| `previous_run_finished` | `maintenance_finished`. |

**Reasons accumulate until the next plan** and then reset. They must survive continue-as-new.

A `stop` does not create a record, because it ends the loop without planning. A stuck run that is given up does not create one either.

**There is no debounce yet**, so a count above 1 only appears when signals pile up while a run is in flight. Spec 3 adds debounce, and its counts land in the same field.

### Linking the record and the run

- The workflow generates the reconciliation id and a prospective run id (both `workflow.uuid4()`) before calling the plan activity and passes both in. The activity stores the run id on the record only when the outcome starts a run; otherwise the id is never used. The plan result returns the reconciliation id.
- **A record must never point at a run that does not exist.** If starting the child workflow fails after the record was stored, the record must not keep claiming a started run. The record is therefore stored after the start was attempted, by its own activity; a failed start records the due operations as `start_failed`.

### Retention

Records older than 30 days are deleted. How and where the deletion runs is the builder's call. Like runs, records are not deleted when a table leaves maintenance; the 30-day retention removes them. Runs are kept at least as long as records (runs have no retention today); if the Maintenance tab is opened at a run it cannot find, it says so ("This run is no longer available") above the run list.

## Dry run

- **Where it lives:** `dry_run: bool` in `MaintenanceSettings` (default false). It follows exactly the rules every other setting follows today between a preset and a table's own settings; this spec adds no new precedence. It is edited on the Settings tab with the other settings, and saving sends `settings_changed` as today.
- **What changes:** in dry run the reconciliation assesses and records as usual. Operations that would start are recorded as `would_start`, and no run is started.
- **Cooldowns do not advance**, because nothing ran. A due operation therefore shows "Would start" at every reconciliation until dry run is turned off.
- **"Run now" still runs in dry run.** It is an explicit request from the user.
- **"Reconcile now" in dry run records "would start" and starts nothing.**
- **Visible state:** while dry run is on, the table header shows it, so nobody wonders why maintenance stopped.

## Reconcile now

A new button beside "Run now". It sends a new `reconcile_now` signal through the existing table-change path (`POST /v1/tables/{uuid}/reconcile`, 202).

- The workflow wakes and reconciles by the normal rules. It differs from "Run now" (`trigger_now`), which skips the assessment and runs the operations the user names.
- If a run is in flight, the request waits and is reconciled when the run finishes, the same as other wakes.

## API

- `GET /v1/tables/{table_uuid}/reconciliations`: newest first, cursor pagination (`before`, `limit`, default 50). Each item is the full record; detail is small.
- `POST /v1/tables/{table_uuid}/reconcile`: Reconcile now.
- `MaintenanceSettings` DTOs gain `dry_run`.
- The OpenAPI document and the Orval client are regenerated.

## Console

A new table tab, **Reconciliations**, placed after Maintenance. The approved mockup is the story `Mockups/Reconcile history` (throwaway; delete it when the real tab lands).

- **List:** a timeline grouped by day, like the Commits tab. One line per reconciliation:
  - the outcome ("Started Rewrite data files", "Would start Rewrite data files" with a Dry run badge, "Nothing to do", "Skipped: table paused");
  - the main wake reason and the time;
  - a link to the run it started.
- **Folding:** consecutive reconciliations with the same nothing-started outcome fold into one line ("4 reconciliations found nothing to do, 06:42–09:42"). The line expands to their times, and each time opens its detail.
- **Detail:** clicking a reconciliation opens a `Drawer` on the right. It shows:
  - the wake reasons with counts, the time, and whether it was a dry run;
  - then one block per operation, ordered started, would start, not needed, cooling down, off, not checked. Each block has a status badge and one reason sentence built from the measurements, e.g. "Because reducible files 1,240 (≥ 5)" or "Not yet: 312 expirable snapshots… next allowed Nov 14, 03:00";
  - a link to the run where one started;
  - "All measurements", collapsed, listing each measurement with observed value, threshold and met or not.
- The run link opens the Maintenance tab at that run (`?run=<id>`), expanding it.
- Status colours follow the console rules: notice for started and would start, neutral for everything else.
- **Reconcile now** sits in the table header next to Run now.
- Page stories cover:
  - the loaded list;
  - folding;
  - the drawer;
  - dry run;
  - empty ("No reconciliations yet");
  - error;
  - phone width.

## Deploying

Running `TableReconciliationWorkflow`s are not migrated: their state gains wake reasons, which old histories cannot replay. The deploy terminates them, and the next discovery sync starts them again (it already re-ensures every live table's workflow). No `workflow.patched` guards, matching the current practice recorded in `docs/agents/known-follow-ups.md`. A run in flight keeps going, but the new workflow does not know about it and may start a second run on the same table; Iceberg's optimistic commits make that wasted Spark work, not corruption. So deploy when no run is in flight (no run without `finished_at`), and say so in the plan's deploy step.

## What is left to the builder

- Table and column layout, indexes, and the retention mechanism.
- How the record is written: by the plan activity, by a separate activity, or both. It is subject to the run-link rule above.
- The exact wording of reason sentences, within the examples above.
- How folding treats a skipped run inside a quiet stretch.
- Whether Reconcile now is disabled while a request is pending.
