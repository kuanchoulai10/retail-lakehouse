# Backend Architecture

## Clean Architecture (Strict Layering)

This project follows "Get Your Hands Dirty on Clean Architecture" with an additional **no-skip-layer rule**: each layer may only depend on the layer directly below it.

```
context.<name>.adapter/inbound  ──> application ──> domain
context.<name>.adapter/outbound ──> application ──> domain
context.<name>.adapter/hybrid   ──> application ──> domain
                                    application ──> base (DDD building blocks)
adapter/*  ──✗──> domain (forbidden: must go through application)
```

Everything below, except `base/`, `bootstrap/` and `entrypoint.py`, lives inside one bounded context, `context/<name>/`. Paths like `application/` and `adapter/` in the rules are relative to that context. Inside `application/` the order is `service` → `port` → `domain/service` → `domain/model`; a ring may import only rings below it, never above (contract `application-ring-order`).

### Backend Structure

Backend code is grouped by **bounded context** first. Inside a context, one **aggregate axis** runs through every layer: each layer directory is split into the same aggregate directories plus `shared` for what spans aggregates. For `table_maintenance` the aggregates are `catalog_discovery`, `table`, `table_discovery_policy`, `table_discovery_policy_attachment`, `table_maintenance_policy`, `table_maintenance_policy_attachment`, `table_maintenance_run`, `table_reconciliation`; for `catalog` they are `catalog`, `namespace`, `table`, `generic_table`, `view`.

```
backend/
├── base/                         # DDD building blocks (imports nothing from the project)
├── bootstrap/                    # Composition roots (knows every context)
│   ├── configs/                  # AppSettings, Component enum, adapter enums
│   ├── container/                # Wiring of services, ports and adapters
│   ├── api.py                    # GLAC_COMPONENT=api
│   ├── worker.py                 # GLAC_COMPONENT=worker (Temporal worker)
│   ├── event_consumer.py         # GLAC_COMPONENT=event_consumer
│   └── migrate.py                # GLAC_COMPONENT=migrate
├── context/
│   └── <name>/                   # One bounded context (today: table_maintenance, catalog)
│       ├── adapter/              # Outermost ring: inbound | outbound | hybrid
│       │   ├── inbound/
│       │   │   ├── web/{aggregate}/      # FastAPI routers, API DTOs
│       │   │   └── event_consumer/       # Polaris catalog event consumer loop
│       │   ├── outbound/{aggregate}/     # SQL, in-memory, catalog, Spark repo/store/gateway adapters
│       │   └── hybrid/                   # Technologies that are both directions
│       │       └── temporal/
│       │           ├── inbound/          # Workflows, activities, schedule setup
│       │           ├── outbound/{aggregate}/  # Signal, start and schedule gateways
│       │           └── contracts/        # Workflow names/IDs, signals, workflow inputs
│       └── application/          # Middle ring
│           ├── domain/model/{aggregate}/ # Entities, Value Objects, Domain Events
│           ├── domain/service/{aggregate}/  # Domain services (planning, rule matching)
│           ├── port/inbound/{aggregate}/ # Use case interfaces + input/output types
│           ├── port/outbound/{aggregate}/  # Repo, Store and Gateway interfaces
│           ├── service/{aggregate}/      # Use case implementations
│           └── exceptions/               # Application-layer exceptions
├── e2e/                          # Black-box scenarios against a deployed platform (see E2e scenarios)
├── entrypoint.py                 # GLAC_COMPONENT env var → api, worker, event_consumer, or migrate
└── tests/
    ├── architecture/             # Rules that run once per context, plus context independence
    ├── base/
    ├── bootstrap/
    └── context/<name>/{application,adapter,fakes}/   # Mirrors the context
```

Import paths carry the context prefix: `context.table_maintenance.application.port...`. `context/` and `context/<name>/` are structural packages (a docstring, no exports, not boundaries).

### Bounded Contexts

Today there are two contexts. `table_maintenance` schedules Iceberg maintenance and persists to SQL. `catalog` serves catalogs, namespaces, tables, generic tables and views with Polaris as the source of truth: each aggregate's `{Aggregate}Repo` has a Polaris HTTP adapter (`adapter/outbound/<aggregate>/polaris/`), nothing is cached, and Polaris errors map to the application exceptions (`NotFoundError` 404, `ConflictError` 409, `ValidationError` 422, `PermissionDeniedError` 403, `CatalogUnavailableError` 502) with Polaris's message as the detail. Every Polaris mapper reads its reply through `read_polaris_reply` (`adapter/outbound/shared/polaris/`), so a reply it cannot read is a 502, never a 500, and required fields are never defaulted. The id value objects refuse U+001F, which joins their parts. `access` is planned next (see `docs/adr/0005-bounded-contexts-and-context-map.md`).

- **Independence rule.** Contexts are independent. A context's `application` imports no other context. A context may import another context only from its own outbound adapters (`adapter/outbound/` or `adapter/hybrid/<tech>/outbound/`), and only through that context's `application.port.inbound` (the outbound adapter calls the other context's use case and maps the result into its own types, anti-corruption style). Inbound adapters, hybrid `inbound` sides and hybrid `contracts` never import another context. Never through another context's domain, services, outbound ports or adapters. `bootstrap` may import every context; `base` imports no context. Enforced by `tests/architecture/test_context_independence.py` (an AST scan, because import-linter wildcards cannot say "another context").
- **No `context/shared`.** Contexts share code only through `base/`. Each keeps its own types (its own table-UUID value object) and links to other contexts by identifier values, not by shared classes. A reference to a table that outlives a request (a row, a workflow id or payload, a published message) is its Iceberg table UUID; a path is for lookup, display and URLs, and a path stored beside the UUID is a display copy that may be stale. Catalogs and namespaces have no UUID and are identified by their path (ADR 0014).

**A table has one maintenance workflow, started by its reconciliation, and its attempts go straight to Volcano.** The `TableReconciliationWorkflow` (`table-reconciliation:table-uuid={uuid}`) plans and starts a `TableMaintenanceWorkflow` child under `table-maintenance:table-uuid={uuid}` (`ALLOW_DUPLICATE`), which runs the planned operations in order, one Spark job each; run ids stay `mr-`. After a run reports, the next run is started only once its workflow closed (bounded by the report activity's worst case; a refused start is recorded `run_start_failed`). An attempt is `queued` until its driver starts; its deadline (`attempt_deadline_seconds`) runs from that start, and one still queued at its own queue wait limit (`queue_wait_limit_seconds`) is polled once more: a driver start read then, or a job read running or completed (its unreadable start taken as that poll), runs it on, and a job still pending ends `queue_timed_out`. A manual run on a table with a run in flight starts no second run: it raises the priority of the run running and of every pending run after it, only upward, and an attempt still `queued` whose job reads `PENDING` is requeued under the same attempt number; one the cluster is still submitting reads `SUBMITTING` and is read again in 5 s, never replaced, since the submit under way would create a driver under the replacement's name. The consumed manual trigger is given back, and planned as a run of its own after this one, when the run left the raise unapplied (it arrived after the run's last attempt ended, or its record failed), received fewer raises than the reconciliation delivered, was given up, or closed without reporting (treated as finished at once by the execution that started it; a run carried through continue-as-new when a raise to it fails and a lookup finds it closed, otherwise at the give-up); it is dropped when the plan fails, the table is skipped, nothing is planned or the workflow is stopping. A changed table priority applies from the next plan. Run-time detail (polling, fencing, requeue, bounds) is in `platform/25-lakehouse-control-plane/README.md`.

**A maintenance run is one operation on one table, and the attempts are its timeline.** `TableMaintenanceRun` holds one `operation`, one stored `RunStatus` (`pending`, `queued`, `running`, `succeeded`, `failed`, `skipped`; there is no `partially_failed`), what its job does (`content`, a `MaintenanceJobContent` of its own operation: the target file size, cutoff time, snapshots to keep and options by their domain names, and for a compaction the `SpecPartitions` it rewrites; stored as `content_json`, ADR 0016), the `metrics` the procedure returns, `error` for a failure and `skip_reason` for a skip, and its `OperationAttempt`s, each with its own `job_name`. The parent `TableReconciliationWorkflow` asks the application for one `mr-` id per planned operation after the plan returns (local activity `issue_run_ids`, ADR 0015), and passes them to the child as `run_ids`; the reconciliation record keeps each id on the operation that started it (`OperationOutcome.run_id`, set exactly when the result is `STARTED`). Before it starts the child, the parent creates every run of the plan `pending`, in one activity and one transaction (`CREATE_MAINTENANCE_RUNS`: all or none, and a retry that finds every run already stored, before or at its insert, returns them), so the record links only runs that exist: a failed create starts no child and records `run_start_failed` with no run, a child refused its start skips the runs created for it (`SKIP_MAINTENANCE_RUNS`) and records the same, and a stop that arrives during the create skips them and drops the plan unrecorded. The child runs them one at a time; a run that ends frees its Spark jobs before the next one submits: each is deleted and polled, as a fence polls, until it reads `NOT_FOUND` with no live pods, however long that takes and recording nothing, so a table has one SparkApplication at a time; the jobs a cancel leaves are waited for the same way before the parent is told. A failed run does not stop the next, and the runs never reached are skipped at the end (`SKIP_MAINTENANCE_RUN`). An attempt whose submit never saved it (a cancel, or a submit refused first) leaves its run `pending`; recording it answers `pending` and counts no record failure, and a run whose submit was refused that way is skipped with the refusal as its `skip_reason`. The submit reads the job from the run's `content` (`gateway_job_of` turns it into the port's typed job), not from its input, and the callback posts to `/v1/table-maintenance-runs/{run_id}/result`.

**A maintenance policy describes the state a table is kept in; the platform decides how often to look and how soon to run again.** `MaintenancePolicyContent` holds a `description`, `on` (`schedule.every_seconds` required, `catalog_commit.debounce_seconds` optional), `dry_run` and one optional block per operation, `{target, options}`; an absent or `null` block means the operation is not done (a policy may hold none), `platform_default()` is the seeded `default` and `GET /v1/maintenance-policies/default` returns it. `target` is what the check compares the table with (`reducible_files.at_most` with `per` `partition` or `table`, `small_manifests.at_most`, snapshot retention, `older_than_seconds`); `per: partition` compacts only the partitions over the target on a scheduled plan (see below). `options` is a typed, curated subset of the Iceberg procedure's arguments, unknown keys refused; an option left out is the procedure's default, and what `target` or the platform owns (`where`, target file size, `older_than`, `retain_last`) is not an option. Cooldowns are not in the policy: `OperationCooldowns` is built from `AppSettings` (`GLAC_MAINTENANCE_REWRITE_DATA_FILES_COOLDOWN_SECONDS` and the other three) and doubles per consecutive failure. A table is checked when its schedule fires, when a catalog commit window closes (the first commit not yet checked opens a window of `catalog_commit.debounce_seconds`, later commits join it without moving its end, any other check but a manual run takes it, and it is carried through continue-as-new), and always for `manual_run`, `reconcile_now`, `policy_changed` and `table_managed` (a table that became managed, sent by discovery and by the catalog event path as the table change `managed`). `table_seen` from a discovery scan only keeps the workflow alive and cancels a `stop`; it counts no wake reason and plans nothing.

**A scheduled `per: partition` compaction selects its partitions from a record of when each went over the target.** `Table.over_target_partitions` holds, for each partition over the target, since when it has been over; a narrow repo write saves it, only when it changes. Two pure functions decide: `track_over_target_partitions` updates the record from the new measurement, and `select_compaction_partitions` picks at most `GLAC_MAINTENANCE_COMPACTION_PARTITIONS_PER_JOB` partitions, those over the target for `GLAC_MAINTENANCE_COMPACTION_MAX_QUIET_WAIT_SECONDS` first (oldest `since` first), then the rest, the most reducible first, leaving out those written within `GLAC_MAINTENANCE_COMPACTION_QUIET_SECONDS` until they have been over the target for `GLAC_MAINTENANCE_COMPACTION_MAX_QUIET_WAIT_SECONDS`. When every partition over the target waits, the verdict and the reconciliation result are `waiting_for_writes` with `next_eligible_at`, and the measurements are `qualifying_partitions`, `selected_partitions` and `waiting_partitions`. The run's content records the selected partitions per spec (`group_partitions_by_spec`; empty means the whole table, also when a selected partition is one no `where` can name), and a manual run always compacts the whole table. The selection reuses `compute_reducible_files` per partition, while `TableMetrics` stays table-level.

**A table's metrics are saved by every plan that observes it and forgotten on every skip.** `PlanTableMaintenanceService` saves a `TableMetrics` (measured from the observation by `measure_table`) in `TableMetricsStore`, one row per table, right after it records the last commit, for manual and scheduled plans, dry run or not; the store only moves `observed_at` forward, so a retried plan with an older observation changes nothing. A skip (unknown table, dropped, unmanaged, not found) deletes the row. A failure to measure, save or delete the metrics is logged and never stops a plan. `GET /v1/table-metrics` is the exporter: it prints 17 gauge series per managed table in the Prometheus text format, reads the store on each scrape, and is hidden from the OpenAPI schema. `GET /v1/tables/{uuid}/metrics/current` reads the saved row, and `GET /v1/tables/{uuid}/metrics?range=1h|3h|6h` reads the trends through `ReadTableMetricHistoryGateway`, whose Prometheus adapter sends one fixed `query_range` selector for the table's uuid (escaped as a PromQL string), only for a uuid the tables repository knows; the browser never sends PromQL, and a Prometheus that cannot answer gives 502. See `docs/adr/0013-table-metrics-in-the-database-and-prometheus.md`.

**A table's last commit and last discovery are observations, not maintenance state** (neither moves `updated_at`). `Table.last_committed_at` is the newest snapshot's commit time, moved only forward wherever the backend reads the table from the catalog: discovery, a catalog event (`ProcessTableHint`) and a reconcile's observation. When only the commit moved, `TablesRepo.record_last_commit` writes that one column (forward-only, never on a dropped table), so a writer holding an older copy never puts back the rest of the row; a full `update` never moves the stored last commit back either. Discovery saves a table only when something about it changed, so instead of a per-table "seen" time a completed catalog-wide scan records one `CatalogDiscovery` per catalog; a live table's last discovery is that time (or its registration, if later), and a table the scan drops keeps the previous scan's time in `Table.last_discovered_at`.

**Which tables are managed is decided by versioned discovery policies attached on the catalog hierarchy, and the nearest attachment wins** (`docs/adr/0012-policies-on-the-catalog-hierarchy.md`). A `TableDiscoveryPolicy` (`dp-`) is a versioned `DiscoveryPolicyContent`: a description, ordered `TableDiscoveryRule`s (value objects with a `dr-` id that links a rule across versions; each holds an outcome, `manage` or `unmanage`, and conditions `{attribute, operator, values}` over `namespace` or `table_name` with `glob`), and a `no_match_outcome`; the first rule whose conditions all hold decides. The seeded default `dp-00000000000000000000000000` has no rules, manages nothing and cannot change. A `TableDiscoveryPolicyAttachment` (`da-`) puts a policy on one `PolicyTarget` (catalog, namespace or table by Iceberg uuid; one attachment per target) and stores the target's catalog, so a scan reads only its catalog's attachments. `PolicyTarget`, `PolicyTargetType`, `candidate_policy_targets`, `enclosing_policy_targets` and `nearest_attached` live in `shared` and serve maintenance attachments too: `decide_table_discovery` walks a table's own attachment, its namespaces deepest first, its catalog, then the default, and the first attachment replaces its parents whole. The decision is recorded on the table as `Table.discovered_by` (a `DiscoveryMatch`: policy id, version and deciding rule id, `None` for the no-match outcome); `matched_rule_id` reads it, and a change of only the match is `MATCH_CHANGED`, saved with nothing sent. **The scanned catalogs are derived, never configured:** `scanned_catalogs` lists each catalog where an attachment points at a policy that `can_manage()` (it has a `manage` rule or a `manage` no-match outcome), and each has the Temporal schedule `table-discovery:catalog={catalog}`. An update, attach or detach runs through `apply_discovery_change`: after the change commits, every affected catalog scanned before or after gets one catalog-wide scan under a fresh change id (`trigger=policy-changed:change={id}`), a catalog that stopped being scanned is unmanaged by that final scan, and then `SyncDiscoverySchedulesGateway` syncs the schedules, deleting only those this change removed; all of it is best effort and logged. The worker start runs `SyncDiscoverySchedulesService`, a full reconcile that fails the start loudly: it creates the missing schedules, gives every catalog that left (a schedule or managed tables, but no managing attachment) a final scan (`trigger=schedule-retired`), and deletes the extra schedules. A scan of a catalog the platform's credential cannot read (`CatalogAccessDeniedError`, from PyIceberg's `ForbiddenError` / `UnauthorizedError`) or that no longer exists records a `CatalogScanFailure` (`cannot_access`, `not_found`) on its `CatalogDiscovery`, changes no table and is not retried; it is current only while newer than the last completed scan, and `GET /v1/scanned-catalogs` shows it. A table the credential cannot load is skipped, never dropped. Attaching needs the target to exist (`ReadTableMetadataGateway.catalog_exists` / `namespace_exists`, so an empty catalog or namespace may be attached; 404 otherwise, 403 for a catalog the credential cannot read), and an attachment is orphaned only when its target no longer exists, for discovery and maintenance alike.

**Maintenance attachments have the discovery attachments' shape, and one route answers what applies of both kinds** (KCL-98). A `TableMaintenancePolicyAttachment` (`pa-`) puts a maintenance policy on one `PolicyTarget`; `GET` and `PUT /v1/maintenance-policies/{name}/attachments` list a policy's attachments and attach it (replacing what the target holds and keeping that attachment's `pa-` id), and `DELETE …/attachments/{attachment_id}` detaches by id (an id of another policy is 404; the catalog is not read, so an orphaned attachment detaches the same way). `/mappings` and both `applicable-policy` routes are gone (404). `GetEffectivePoliciesService` (`service/table/get_effective_policies.py`, in the `table` package because it answers for a place in the catalog) serves `GET /v1/tables/{uuid}/effective-policies` (a table maintenance records, 404 otherwise) and `GET /v1/effective-policies?catalog=&namespace=&table=` (by location, namespace dot-joined; a catalog, namespace or table the catalog does not hold is 404, a catalog the platform cannot read 403). Both answer `{"policies": [maintenance entry, discovery entry]}`, a list discriminated on `kind`, so a third kind adds an entry: each names `policy_id`, `policy_name`, its latest `version` (an attachment always means the latest), `description`, the nearest attachment's `target` and its `attachment_id` (both null for the platform default); the maintenance entry adds `dry_run`, the discovery entry `no_match_outcome`. **Every kind walks the same candidates** (`policy_candidates` in `service/shared/`, also used by `ResolveApplicableTableMaintenancePolicyService`, so planning and the answer cannot drift) and takes its own nearest attachment, so a table attachment of one kind leaves the other kind at its own level. `policy_target_from_request` only builds a target from a request and checks it exists in the catalog.

**A table's properties are shown against a catalogue of known Iceberg properties** (`iceberg_table_property_catalogue()` in `context/catalog/application/domain/model/table/`): each entry has its Iceberg default, a description and whether a reset may touch it, pinned to one Iceberg version (today 1.10.1, the Spark runtime's `GLAC_SPARK__ICEBERG_VERSION` and Polaris 1.8.0's); update the defaults with that version. `resolve_table_properties` gives every catalogue key, every key the table sets and every key the catalog defaults a default: the catalog's `table-override.<key>` (forced, never resettable), else its `table-default.<key>`, else Iceberg's. A reset (`POST …/tables/{table}/properties/reset`) goes through the uuid-guarded property update: it removes a key, but writes the default back when a new table would hold it explicitly (a catalog default, which Polaris applies only at create, and `write.parquet.compression-codec`, which Iceberg writes on every new table). A key is modified when its value differs from its default, or, unset, when the reset would write the default (the default shown does not apply); a custom key is modified only when it has no default or is off it. `created-at` is written by Polaris (`set_by_catalog`): no default, never modified. `format-version`, `gc.enabled`, `created-at` and forced keys refuse the whole reset with 422.

**A table's schema and partition spec versions are compared by id, never by name, and computed on every request from the Polaris metadata** (`compare_schemas` and `compare_partition_specs` in `context/catalog/application/domain/service/table/`). Schema fields match by Iceberg field id (a renamed or promoted field is one row, a nested field is a row of its own with its full path); partition fields match by partition field id, and a removed plus an added field on the same source column pair into one `transform_changed` row. The previous version is the next lower id, the first version has no base and lists every field unchanged, and `Table.current_schema_id` / `default_spec_id` (not the highest id) mark the current one. Four routes under `/v1/catalogs/{catalog}/namespaces/{namespace}/tables/{table}`: `GET schema-versions`, `GET schema-versions/{schema_id}/comparison?base=<id>`, `GET partition-spec-versions` and `GET partition-spec-versions/{spec_id}/comparison?base=<id>`; an omitted `base` means the previous version and an unknown version or base is 404. The domain reads no adapter text: a partition field's transform is a `PartitionTransform` (kind, bucket or truncate argument, and the raw text of a transform it does not know, kept so it round-trips), which the Polaris adapter parses and `text()` writes back; a schema field carries `SchemaField.kind` (primitive, struct, list or map), set by the adapter from the JSON type and the source of its outer type; whether a partition field still has the name a writer gives by default is `DefaultPartitionFieldNames` (the Java and Python writers' forms), so only a name someone chose reads as renamed. The `transform(column)` expression the comparison returns is written by the web mapper, `#<id>` for a column no schema holds.

### Adding a context

1. Create `context/<name>/__init__.py` and `context/<name>/{application,adapter}/`, and mirror them under `tests/context/<name>/`.
2. Create all four application rings: `service`, `port`, `domain/service` and `domain/model`. The `application-ring-order` layers contract uses `containers = context.*.application`, and import-linter requires every layer to exist in each container.
3. The architecture tests (`context_names()` in `tests/architecture/contexts.py`) and the `context.*` import-linter contracts pick the new context up without edits. Two guards keep it that way: no architecture test except `test_aggregates.py` names `table_maintenance`, and no contract names a concrete context.
4. Wire it in `bootstrap/`. Its web adapter exposes `register_routes(app, use_cases)` in `adapter/inbound/web/register_routes.py`, which keeps its use cases on `app.state` under its own key, adds its error handlers and mounts its routers under `/v1`; `bootstrap/container/build_api_app.py` passes one registration per context to `create_api_app`, so all contexts share one FastAPI app. A context that persists to SQL gets its own `adapter/outbound/shared/sql/` (its own metadata, `create_schema` and hand-written `AGGREGATE_SQL_PACKAGES`) with a mirrored drift test like `tests/context/table_maintenance/adapter/outbound/shared/sql/test_create_schema.py`. Never add one context's SQL packages to another context's list. `run_migrations` (`bootstrap/container/run_migrations.py`, called by `bootstrap/migrate.py`) calls each context's `create_schema`.
5. A context must have `adapter/inbound/web` and `adapter/outbound`. `adapter/inbound/event_consumer` and `adapter/hybrid/<tech>` are optional; a hybrid technology directory that exists holds exactly `inbound`, `outbound` and `contracts`. Every aggregate has exactly one repository port in its own context (`test_each_aggregate_has_one_repository_port_per_context`).

### Rules

- **Domain** depends only on the stdlib, `base` and Pydantic (`pydantic`, `pydantic_core`, `annotated_types`). Enforced by `test_domain_dependencies.py` (allow-list) and contract `domain-pure`.
- **Application** depends on domain and base, in ring order. No adapter, no bootstrap, no framework imports. Services, ports and exceptions do not import Pydantic directly; they reach it only through the domain and `base` (ports through `UseCaseInput` / `UseCaseOutput`, `docs/adr/0010-pydantic-in-inbound-ports.md`). Enforced by contracts `application-ring-order`, `application-no-outer-rings` and `application-outer-rings-pydantic-free`.
- **Adapter** imports application only through ports and exceptions (not domain directly). Web adapter catches application-layer exceptions, not domain exceptions. Enforced by contract `adapters-see-only-ports`.
- **Adapter directions are independent.** `inbound`, `outbound` and `hybrid` do not import each other, a hybrid technology's `inbound` and `outbound` sides do not import each other, and inbound channels (`web`, `event_consumer`) are independent. Contracts `adapter-directions-separate`, `hybrid-directions-separate`, `inbound-channels-independent`. Layout: `tests/architecture/test_adapter_layout.py`.
- **Hybrid contracts** (`adapter/hybrid/<tech>/contracts/`) depend only on stdlib, base and ports, and only the same technology imports them. Contracts `hybrid-contracts-neutral`, `hybrid-contracts-private`. Temporal contracts are one package per workflow (`table_reconciliation`, `table_maintenance`, `table_discovery`) plus `shared` (task queue, `TableSearchAttribute` names of the search attributes registered by `platform/21-temporal`), each with short module names (`workflow_name.py`, `workflow_id.py`, `workflow_input.py`, `signal.py`, `activity.py`, `summary.py`); a signal lives with the workflow that receives it, an activity name with the workflow that calls it, and signal and activity names are StrEnums whose string values are pinned by `tests/context/table_maintenance/adapter/hybrid/temporal/contracts/test_wire_names.py`. Activities are grouped by workflow: each contract package's `XActivity` enum has exactly one `XActivities` class in `inbound/activities/` (`TableReconciliationActivities`, `TableMaintenanceActivities`, `TableDiscoveryActivities`) holding every method that enum names, and that class takes the constructor dependencies its methods use. Each method wraps exactly one inbound port, except the signal wiring (`SIGNAL_PARENT`, `GET_WORKFLOW_RUNNING`), which calls the Temporal client instead. Enforced by `tests/architecture/test_temporal_activity_grouping.py`. Temporal workflows import only Temporal and their contracts: contract `temporal-workflows-sandbox-safe`, plus `tests/architecture/test_temporal_workflow_sandbox.py` (Temporal's own sandbox validation) and `test_temporal_workflow_determinism.py`. A workflow never mints an id: the reconciliation workflow takes its reconciliation id and its run ids from the application through local activities (`ISSUE_RECONCILIATION_ID`, `ISSUE_RUN_IDS`), whose recorded results a replay reads back, and issuing run ids stays a step of its own before the create, so a create retried after it stored its runs never issues new ids (KCL-99, ADR 0015).
- **An aggregate changes only through its own methods.** No code in a context (domain services, other aggregates, application services, ports, adapters) assigns or deletes an attribute (or an item of one) of an object it holds, calls another object's private method, or writes one reflectively (`setattr` / `delattr` / `vars` on another object and any other use of `setattr` / `delattr`, `getattr` of a private or dunder name, `__setattr__` / `__delattr__` / `__setitem__` / `__delitem__` / `__init__` / `__setstate__` / `__replace__` / `__ior__` / `__getattribute__` on another object, a method called through a builtin type or `BaseModel` such as `dict.update(m, …)` or `object.__setattr__(…)`, another object's `__dict__`, `copy.replace` / `dataclasses.replace`, `model_copy(update=…)`, `model_construct(…)`); it calls the aggregate's methods instead. Every bound target counts: assignment, `del`, `for`, `with … as` and comprehensions. Only its own attributes (`self.…`), Starlette's `app.state` and `request.app.state` (no other `.state`) and its own class's private helpers (`Schema._walk`, `type(self)._clamp`) are allowed. An object built in the same function counts as another object: build it with its values in one call. Domain model collections cannot be edited in place at all (see `ReadOnlyMapping` below). Enforced for every file of every context by `tests/architecture/test_state_changes_through_methods.py`.
- **No compatibility code during development.** A change to stored data, a payload or workflow behaviour ships without fallbacks for old data, without `workflow.patched`, and with a cluster rebuild; `tests/architecture/test_temporal_workflow_determinism.py::test_no_workflow_calls_patched` guards the patches.
- **Adapters do not import bootstrap**, and **Configs** (`bootstrap/configs/`) is cross-cutting: it must not depend on any bounded context. Contracts `adapters-no-bootstrap`, `configs-leaf`. **Base** depends on nothing project-internal: contract `base-isolation` (its forbidden list is every other root package, `test_base_imports_no_project_package`). **Application exceptions** are a leaf: they import no other application ring, adapter or bootstrap (contract `application-exceptions-leaf`).
- **Aggregate axis.** Every layer directory is split by the same aggregate names, with no loose modules at a layer root (only the web adapter's `register_routes.py` and `error_handlers.py`). Enforced by `tests/architecture/test_aggregate_axis.py`. A context's aggregates are derived: they are the directories under its `application/domain/model/` (except `shared`) whose package defines an `AggregateRoot` subclass (`tests/architecture/aggregates.py`, `aggregates(context)`), and every other layer may hold only those names plus `shared`, except `application/port/inbound`, which mirrors the service aggregates without `shared` (`test_inbound_ports_match_services`). A context-wide read model's use case files under the aggregate that owns its route; today platform settings sits under `table_maintenance_run`. Adding an aggregate means adding its `AggregateRoot` and updating its context's `AGGREGATE_SQL_PACKAGES` in `adapter/outbound/shared/sql/create_schema.py` (guarded by that context's `test_create_schema.py`). `AGGREGATE_SQL_PACKAGES` is per context and stays hand-written.
- **The application writes no Iceberg call.** Iceberg's option names, the `where` Spark SQL, a time written as text (`isoformat`, `strftime`) and `procedure_*` functions live only in the k8s Spark adapter (`iceberg_procedure_args`, `spark_where_clauses`), which turns a run's typed job into `GLAC_REQUEST` (ADR 0016). Enforced by `tests/architecture/test_no_engine_spelling_in_application.py`.
- **Ports speak intent, not infrastructure.** Names in `application/` carry no infrastructure vocabulary (`temporal`, `workflow`, `signal`, `activity`, `spark`, `k8s`, `kubernetes`, `sql`, `pyiceberg`, `iceberg_rest`, `kafka`, `polaris`, `pod`, `driver`, `executor`, `heap`, `callback`, `signalled`, each with its plural and inflected forms, since a term matches whole words); a port names what the application wants (`SendTableChangeGateway` with a `TableChange`), the adapter picks the mechanism. A job is a coordinator and its workers (the Spark driver and executors), it runs as processes (pods), and it reports its result (the callback); the k8s adapter translates the Spark roles and the runtime writes `result_report_url` and the `peak_coordinator_memory_bytes` / `peak_worker_memory_bytes` metrics. Enforced by `tests/architecture/test_no_infrastructure_terms.py`.
- **Boundary-only imports.** A package with an `__init__.py` is a boundary; other packages import from it with `from <boundary> import Name`, never from a module inside it. Boundaries do not nest, and every module belongs to one (except the `bootstrap` entry modules `api`, `worker`, `event_consumer`, `migrate`). Enforced by `tests/architecture/test_import_boundary.py` (derived rules in `tests/architecture/boundaries.py`).
- **Import-linter has no exemptions.** `.importlinter` holds 17 named contracts and no `ignore_imports`. Enforced by `tests/architecture/test_importlinter_config.py`; run `lint-imports` to verify.
- **Ruff config only extends the root.** The backend `[tool.ruff]` extends the root `ruff.toml` and adds only isort first-party and flake8-type-checking lists; never add ignores, selects or rule-threshold overrides to the backend pyproject. Enforced by `tests/architecture/test_ruff_config.py`.
- **Long import heads keep `# noqa: E501`.** A `from <module> import (` head that cannot fit in 120 characters (long port and adapter paths that follow the naming rules) carries `# noqa: E501`; the owner accepted these markers on 2026-11-07, so do not rename modules to shorten them. Any other line must fit.
- **Naming and structure.** Inbound ports, outbound ports, services and web DTOs follow the naming tables below: `test_inbound_port_structure.py` and `test_inbound_port_models.py`, `test_outbound_port_structure.py`, `test_service_structure.py`, `test_dto_naming.py`; top-level layout `test_directory_structure.py`; inheritance depth `test_inheritance_depth.py`.
- **DTOs live in the adapter.** `UpdateTableDiscoveryPolicyApiRequest`/`TableDiscoveryPolicyApiResponse` are in `adapter/inbound/web/table_discovery_policy/dto.py` with plain types (no domain enums).
- **Use case results live in the application layer.** Services convert domain objects to `UseCaseOutput` models (ADR 0010) so adapters never see domain types.
- **Bootstrap** is the only layer allowed to import from all other layers. It is the composition root.
- **Single image, four components**: `GLAC_COMPONENT=api` (default), `worker`, `event_consumer`, or `migrate` via `entrypoint.py`.
- **Unified settings**: All configuration via `GLAC_` prefixed env vars (pydantic-settings). Nested with `__` delimiter: `GLAC_MAINTENANCE_MAX_ATTEMPTS`, `GLAC_TEMPORAL__ADDRESS`.

## E2e scenarios

`e2e/` is a pytest package of scenarios that check a deployed platform from outside, beside `tests/`, which never imports it. It imports none of `base`, `bootstrap` or `context` and they never import it (contracts `e2e-black-box`, `e2e-not-imported`); it reaches the platform only as a client: the API (`PlatformApi`), Polaris (`PolarisClient`, and PyIceberg for tables), Temporal (`TemporalSession`, the async client on one event loop) and RustFS (`pyarrow.fs.S3FileSystem`). It talks to no query engine, so it runs with Trino stopped. Its dependencies are the `e2e` group in `pyproject.toml` (pytest, `pyiceberg[pyiceberg-core]`), exported to `requirements-e2e.txt` by the `uv-export-backend-e2e` hook; the `table-maintenance-e2e` image (`e2e.Dockerfile`) adds them and `e2e/` on top of the production image, which keeps excluding them (`.dockerignore`), and `build.sh` gives the backend image a tag that ignores these files. Run it in the cluster with `platform/25-lakehouse-control-plane/e2e/run.sh critical|full` (wave README, "End-to-end check").

A scenario is a test module marked `critical` (finishes in minutes; pre-merge) or `full` (nightly; `full` runs both), with strict markers; collection refuses a scenario marked neither or both, since it would never run or run twice. It names what it creates with the run's `suffix` fixture and pushes each undo on the `cleanup` fixture right after the create succeeds, so a failed run cleans up too; the stack runs newest first, runs every undo even when one fails, and a failed undo fails the test. `ManagedTable.create` gives a scenario a table the platform manages, in a namespace of its own with its own maintenance and discovery policies, and its undo order keeps the platform off a half-removed table. A module that attaches policies, scans or compares against the defaults takes the `owned_catalog` fixture, a catalog of its own (`OwnedCatalog`, `tm_e2e_catalog_<suffix>_<module>`), so the shared `iceberg` catalog's scans never change; `revoke_reads` / `restore_reads` take and give back `catalog_admin`'s content grants to make it unreadable, and `drop_catalog` gives them back before emptying it. The worker restart scenario uses `KubernetesApi` with the pod's ServiceAccount, whose Role allows only `get` and `patch` on the worker Deployment (`platform/25-lakehouse-control-plane/e2e/rbac.yaml`). Every name a scenario gives comes from `OwnedNames`, whose patterns the session-start sweep (`sweep_leftovers`) removes by, so what a cut-short run left goes on the next run; a new kind of resource gets a builder and a pattern there and a step in the sweep. A SIGTERM interrupts pytest (`interrupt_on_sigterm`), so the running scenario's cleanup still runs. Waits are `wait_until` with a timeout and the state last seen; a probe that raises counts as "not yet". Support code is one object per file in `e2e/support/`, re-exported from `e2e.support`, and its logic is unit-tested in `tests/e2e_support/`, which the pre-pr gate runs; the scenarios themselves run only on a cluster.

## Mutation testing

`task -d src/data-platform/backend mutation-test MUTANTS='<glob>'` runs mutmut over the mutants whose names match the glob (module paths, for example `MUTANTS='context.table_maintenance.application.domain.model.table.*'` or `'base.entity*'`) and lists the survivors; `uv run mutmut show <name>` prints one mutant's diff. Run it over the modules a change touches, then kill each survivor with a test or say why it is equivalent. mutmut copies `base` and `context` into `mutants/` (git-ignored, throwaway) and rewrites every function behind a trampoline, so the architecture tests, which read the source tree, are left out of its runs (`[tool.mutmut]` in `pyproject.toml`). The mutated modules import `mutmut`, and the active mutant lives in that module, so `tests/conftest.py` passes `mutmut` through Temporal's workflow sandbox when mutmut runs the tests. `task gates:nightly` runs it over the whole backend (`MUTANTS='*'`, hours) and lists the survivors without failing. The workflow modules are left out (`do_not_mutate`): a mutated wait condition leaves a workflow waiting, and mutmut times out only on CPU time, so such a mutant would never end; a workflow change gets two to four hand-made mutants instead. A line whose mutants are all equivalent carries `# pragma: no mutate`.

## DDD Base Types (`base/`)

DDD building blocks on Pydantic v2 (stdlib, `pydantic`, `pydantic_core` and `annotated_types`, nothing from the project). Import everything from `base`.

The domain model types, all strict (no coercion: `True` is not an `int`, a `list` is not a `tuple`, a plain `str` is not a `StrEnum`) and `extra="forbid"`:
- `ValueObject` — frozen, equality by value. A subclass declares fields, no decorator: `class Money(ValueObject): amount: int; currency: str`. Invariants go in `field_validator` / `model_validator(mode="after")` raising plain `ValueError`. Wire input goes through `Money.from_primitives(data)` (strict JSON mode, only the wire names / aliases are accepted); wire output through `to_primitives()` (JSON primitives keyed by alias). Never `model_validate` wire data directly.
- `EntityId` — a `RootModel[str]`, frozen, built positionally: `class OrderId(EntityId): pass`, `OrderId("1")`; `.value` gives the string. Ids of different kinds never compare equal. An id kind this platform mints declares `PREFIX: ClassVar[str | None] = "mr"` (ADR 0011): every construction path then refuses any value but `mr-<26 base32 characters>` with `InvariantViolation` (`TableMaintenanceRunId must look like mr-<26 base32 characters>`), and `TableMaintenanceRunId.new()` mints one: a UUIDv7 as 26 lowercase base32 characters (the TypeID suffix encoding), so ids sort by time (`TypeError` without a `PREFIX`; a bad `PREFIX`, not 2 to 8 lowercase letters, raises `ValueError` when the class is defined). `.suffix` is the part after `<PREFIX>-` (the k8s adapter names Spark applications by it), and `EntityId.is_shaped_like_an_id(text)` tells whether text is shaped like an id of any prefix (policy names are refused when it is). The id format lives only here, as private functions of `base/entity_id.py`; the table maintenance id types live in `domain/model/shared/`, so aggregates reference each other by typed ids (`RecordedAttempt.run_id` is a `TableMaintenanceRunId`). `PREFIX` is a class variable, so the dump, JSON and `str` stay the bare string. Without `PREFIX` any string is accepted. Every context id type is listed in `tests/architecture/test_prefixed_ids.py` as `EXPECTED_PREFIXES` (with its prefix), `UNPREFIXED` or `PENDING` (to be prefixed; may not exist yet), and no prefix is used twice; a new id type gets a row there.
- `Entity[ID]` — `class User(Entity[UserId]): name: str`; equal and hashed by class and `id`, and its `id` cannot change after creation (assigning it, or passing it to `_assign_together`, raises `AttributeError`). `validate_assignment=True`, and an assignment is atomic: a rejected one (field or cross-field after-validator) leaves the entity unchanged. Fields checked together by a cross-field validator are changed in one step with `self._assign_together(a=..., b=...)` (only the changed fields), never one after the other and never through `__dict__`. Reassign containers (`self.x = (*self.x, v)`, `self.m = {**self.m, k: v}`); they cannot be mutated in place.
- `ReadOnlyMapping[K, V]` — the type of every mapping field of a domain model (`properties: ReadOnlyMapping[str, str] = Field(default_factory=dict)`). An annotated `Mapping`: the field accepts a dict, validates it as `dict[K, V]` and holds a frozen copy (nested dicts, lists and sets frozen too; any other mutable collection is refused) that raises `TypeError` on any in-place edit and equals the JSON it came from (a frozen tuple equals its list), while type checkers see a `Mapping` with no editing methods; dumps give plain dicts and lists, and the frozen copy encodes as JSON, hashes, copies and pickles. A domain model field holds no `list`, `dict` or `set` at any depth, only `tuple`, `frozenset` and `ReadOnlyMapping` (`tests/architecture/test_domain_collections_are_immutable.py`), and the model bases set `validate_default=True` so a default is frozen too. A consumer that needs a plain dict copies it (`dict(run.metrics)`); a helper that only reads takes a `Mapping`. Python 3.15's builtin `frozendict` can replace the frozen type later.
- `AggregateRoot[ID]` — `class Order(AggregateRoot[OrderId]): total: int`; an Entity that records events with `register_event()` and hands them over with `collect_events()` (a private attribute, never dumped or compared).
- `DomainEvent` — frozen, `class OrderPlaced(DomainEvent): order_id: str`; `occurred_at` defaults to now (UTC).
- `ValueObject.with_changes(**changes)` — a changed copy of a value object that runs every validator. Domain code never calls `model_copy` (it skips validation), and never copies an aggregate (pending events would be lost).
- `InvariantViolation` — the `ValueError` the model bases raise, chained from Pydantic's error, on these paths: construction (including `EntityId("…")`), `from_primitives`, `model_validate` / `model_validate_json`, `with_changes`, and entity attribute assignment (including `_assign_together`). Validating a base through a Pydantic `TypeAdapter` raises Pydantic's own error; adapters never do this, and they never import the domain directly (contract `adapters-see-only-ports`). The violation's text is one line, the first error as `<dotted.loc>: <msg>` (just `<msg>` for a model-level rule); an inner model's violation raised inside an outer validator comes out of the outer model as one violation. Services use `str(exc)` and never import Pydantic. A broken invariant answers 422 with that line; `InvalidTableTransition` / `InvalidRunTransition` still answer 409. Tests expect `pytest.raises(InvariantViolation)`, never Pydantic's `ValidationError`.
- `UseCaseInput` / `UseCaseOutput` — the inbound port models (ADR 0010): frozen, strict, `extra="forbid"`, raising `AttributeError` like the model bases. A refused input raises `InvariantViolation`; a refused output raises builtin `TypeError` chained from Pydantic's error, because only our services build outputs, so a refused one is a server bug: no edge handler catches it, and it surfaces as a logged 500, a retryable Temporal failure, or a hint the consumer retries and logs. Tests expect `pytest.raises(TypeError)` for a refused output. Fields hold primitives and stdlib types only (`str`, `int`, `float`, `bool`, `None`, `datetime`, `timedelta`, `tuple`, `dict`) and classes nested one level inside, each extending the same base and named by what it holds (`ListTableCommitsUseCaseOutput.Commit`); never a domain type. An entry point holding a dict of JSON primitives builds an input with `{Name}UseCaseInput.from_primitives(data)` (strict JSON mode: ISO strings become `datetime`, arrays `tuple`), a tolerant reader that ignores unknown keys at every depth but refuses missing or mistyped ones, so a newer workflow's extra key does not break an older worker during a rolling deploy; code builds by keyword, where an extra key is still refused. An `InvariantViolation` at an edge is a client error, like `ValidationError`: 422 from each context's web error handlers, a non-retryable Temporal `ApplicationError`, a hint the event consumer drops without retry. Each `input.py` / `output.py` defines one top-level class and the use case's `__init__.py` exports exactly its three names, checked for every use case by `tests/architecture/test_inbound_port_models.py`.
- **Rules for writing port models** (ADR 0010, `docs/adr/0010-pydantic-in-inbound-ports.md`):
  - A sequence field is `tuple[...]`, never `list[...]` or `set[...]` (strict mode refuses a `list` for a `tuple`; `from_primitives` turns a JSON array into a `tuple`). A field holds only `str`, `int`, `float`, `bool`, `None`, `datetime`, `timedelta`, a `Literal`, a `tuple[...]` or `dict[...]` of these, a class nested in the same port file, or a union of these; `Any` only inside a `dict` or `tuple`. Enforced by `tests/architecture/test_inbound_port_field_types.py`.
  - A structured dict (a settings blob, a Spark request, an Iceberg schema or summary) stays `dict[str, Any]`; do not invent a nested model for what the application only passes through.
  - A nested type is a class nested in the input or output, named by its noun (`ListTableCommitsUseCaseOutput.Commit`, `PlanTableMaintenanceUseCaseOutput.Check`), at most one level deep, never a second top-level `…Item` class. Do not add a `…Item` class.
  - `from_primitives` is a tolerant reader: it ignores unknown keys at every depth and still refuses missing or mistyped ones. Use it for what another process wrote (a Temporal payload, an event); build by keyword in code, where an unknown key is refused.
  - A port field is never named after a `BaseModel` attribute (`schema`, `json`, `copy`, `dict`, `validate`, `construct`) or a port base attribute (`from_primitives`); name it by what it holds (`table_schema`, `view_schema`). Enforced by `tests/architecture/test_inbound_port_field_names.py`.
  - Do not edit a web DTO's docstring casually: the docstrings of `ApiRequest` / `ApiResponse` classes and their fields are the descriptions in the published OpenAPI document, which the console's generated client is built from (the `gates:pre-pr` contract test fails on a change). Change one only when the published description should change.
- Assigning to a frozen model (`ValueObject`, `DomainEvent`, `EntityId`) and `del` of a field of any model (an `Entity` too) raise Python's builtin `AttributeError`, not `InvariantViolation`: a mutation is a programming error, so it surfaces as a 500, not a 422. The message names the class; a value object's points at `with_changes`. Tests expect `pytest.raises(AttributeError, match="is immutable")` for frozen assignment.

`base` exports only the allowlisted building blocks: `ValueObject`, `Entity`, `EntityId`, `AggregateRoot`, `DomainEvent`, `InvariantViolation`, `ReadOnlyMapping` (added 2026-11-24: every context's domain models need one immutable mapping type, KCL-100), `Specification`, `Repository`, `Store`, `Gateway`, `UseCase`, `UseCaseInput`, `UseCaseOutput`, `EventHandler`, `EventDispatcher`, `UnitOfWork` (not all exist yet). Helpers and shared types such as `WholeSeconds` belong to the context that uses them. Private `_` modules in `base/` are implementation details used only inside `base/`; nothing outside imports them. Both rules are enforced by `tests/architecture/test_base_building_blocks.py`. To add to `base`, edit the allowlist in `tests/architecture/test_base_building_blocks.py` and say why here.

Concrete domain types extend these bases directly (max depth 1, checked at class creation and by `test_inheritance_depth.py`). The five model bases and the two port model bases are listed in ruff's `runtime-evaluated-base-classes` (`test_every_pydantic_base_is_runtime_evaluated`), so field-type imports stay at runtime; import the base from `base`, never `pydantic.BaseModel` directly.

The ports and helpers:
- `EventHandler[E]` — ABC for handling one domain event type
- `EventDispatcher` — concrete (non-subclassable) router from events to handlers
- `Repository[E]` — generic persistence ABC
- `Store` — infrastructure persistence (not aggregate)
- `Gateway` — external system interaction
- `UseCase[TInput, TOutput]` — single `execute()` method

## Outbound Port & Adapter Naming Convention

Three base classes define all outbound ports (in `base/`):

| Base Class | When to use | Port format | Adapter format |
|------------|------------|-------------|----------------|
| `Repository` | Aggregate persistence | `{Aggregate}Repo` | `{Aggregate}{Tech}Repo` |
| `Store` | Infrastructure persistence (not aggregate) | `{Noun}Store` | `{Noun}{Tech}Store` |
| `Gateway` | External system interaction | `{Verb}{Noun}Gateway` | `{Verb}{Noun}{Tech}Gateway` |

**Gateway verb vocabulary** (new verbs require review): `Read`, `Submit`, `Send`, `Publish`, `Poll`, `Sync`, `Write`, `Delete`, `Update`, `Create`.

**Gateway directory structure** (under `port/outbound/{aggregate}/`):
```
{verb}_{noun}/
├── __init__.py       # re-export all symbols
├── gateway.py        # {Verb}{Noun}Gateway (extends Gateway)
├── input.py          # {Verb}{Noun}GatewayInput (optional, primitive-only)
└── output.py         # {Verb}{Noun}GatewayOutput (optional, primitive-only)
```

A gateway directory may also hold extra single-class files (for example `list_input.py`). Except `list_input.py`, which defines `{Verb}{Noun}GatewayListInput`, each defines one class named after its file stem in CamelCase (`{CamelCaseStem}`), primitive-only like `input.py`. The extra file names are the fixed allowlist `GATEWAY_EXTRA_FILES` in `test_outbound_port_structure.py`, which enforces this.

Input/output files and the extra files must only use primitive types (`str`, `int`, `float`, `bool`, `dict`, `list`, `tuple`, `None`) and `datetime`. They may import `base.value_object.ValueObject` but nothing from `application.domain` or other `base.*` modules. They may also import the extra files of their own gateway directory (for example `job_container_exit.py`, a list item of the output, or `job_partition_spec.py`, part of a submitted job), since those are held to the same primitive-only rule. This is enforced by `test_outbound_port_structure.py`.

Choosing between the three is decided by whether the thing is one of our aggregates, not by where its data lives (`docs/adr/0006-choosing-an-outbound-port.md`). An operation whose external system returns a secret only once is a `Create`/`Update` Gateway, not a Repository method (`docs/adr/0007-one-time-secrets.md`). The contexts and how they relate: `docs/adr/0005-bounded-contexts-and-context-map.md`.

See `docs/superpowers/specs/2026-04-27-outbound-port-adapter-naming-convention.md` for full spec.

## DTO Naming Convention (Layer Suffixes)

Each DTO class carries a layer-specific suffix so its origin is unambiguous at a glance:

| Layer | File | Suffix | Example |
|-------|------|--------|---------|
| Inbound port | `port/inbound/{aggregate}/{verb}_{noun}/input.py` | `UseCaseInput` (the class extends `UseCaseInput`) | `CreateJobUseCaseInput` |
| Inbound port | `port/inbound/{aggregate}/{verb}_{noun}/output.py` | `UseCaseOutput`; a nested type is a nested class named by its noun, not a second top-level class | `CreateJobUseCaseOutput`, `ListTableCommitsUseCaseOutput.Commit` |
| Outbound port | `port/outbound/{aggregate}/{verb}_{noun}/input.py` | `GatewayInput` | `SubmitJobRunGatewayInput` |
| Outbound port | `port/outbound/{aggregate}/{verb}_{noun}/output.py` | `GatewayOutput` | (none yet) |
| Web adapter | `adapter/inbound/web/{aggregate}/dto.py` | `ApiRequest` / `ApiResponse` | `CreateJobApiRequest`, `JobApiResponse` |

**Prefix rules:**
- Port layers (inbound/outbound): class prefix must match the PascalCase form of the parent directory name. Enforced by `test_inbound_port_models.py` (inbound input and output), `test_inbound_port_structure.py` (inbound use case) and `test_outbound_port_structure.py`.
- Web adapter: no prefix rule enforced. Verb prefix is convention for endpoint-specific request DTOs (e.g., `CreateJobApiRequest` over bare `JobApiRequest`); shared resource responses and nested sub-components may use noun-based names. Suffix enforced by `test_dto_naming.py`.

See `docs/superpowers/specs/2026-04-28-dto-naming-convention-design.md` for full spec.
