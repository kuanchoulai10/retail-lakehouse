# Console UI

Rules for `src/data-platform/frontend` pages. **Build pages from `@retail-lakehouse/design-system` (rules in `src/design-system/CLAUDE.md`); domain components stay here.**

- **Import the design system only from `@retail-lakehouse/design-system`.** No deep paths, `radix-ui`, `@radix-ui/*`, `lucide-react`, `@serendie/*` or `@tabler/*`. Icons come from the design system.
- **A missing component goes to the design system**, with its story and keyboard test, not into the console. Domain components (`MaintenanceGate`, `ConfirmDeleteDialog`'s wording, `ActionsMenu`) stay here, built from design-system parts.
- **Semantic utilities only** (`bg-surface`, `text-on-surface-variant`, `border-outline`, `text-negative-text`). No raw hex, arbitrary or Tailwind palette colours, no `--sd-*`, no old shadcn names (`bg-background`, `text-muted-foreground`, `border-border`), no `dark:`. Enforced by `src/test/designSystemBoundary.test.ts`.
- **Status colours only for status.** Not due, cooldown and disabled stay neutral; notice = due operation or truncated count; negative = error or failed run; positive = succeeded run only. Use `StatusBadge`; bare status text uses `negative-text`, `positive-text`, `notice-text`.
- **Category badge for belonging, not for health.** `CategoryBadge` (via `TableStatusBadge`) shows which group a table is in on the Tables page's Status column only: managed is the theme colour's light tint (`accent`, no border or hover, so it does not read as a button), unmanaged is grey (`neutral`), undecided (a table a policy was attached to before discovery saw it, which discovery has not decided yet) is grey too (`neutral`, reading "Undecided"), dropped is a fainter grey, struck through and italic (`muted`). It never uses the status colours, and `StatusBadge` is never used for managed, unmanaged, undecided or dropped. Use it for another grouping only when it says which group, never how it is doing; the text always stays.
- **Theme colour for interaction, as Serendie does** (rules in `src/design-system/CLAUDE.md`, Colour use). Every text link is a `TextLink` wrapping the router `Link` (`asChild`), with `inline` inside a sentence; never style a `Link` by hand. The one exception is a link to another app on the gateway (the Temporal UI at `/temporal`): it is a `TextLink` wrapping a plain anchor (`<TextLink asChild><a href=...>`), because the router `Link` would put the console's `/console` base path in front of it.
- **Identifiers in `font-mono`** (procedure names, snapshot ids, file paths, `execution_ref`, property keys / values, schema types); `tabular-nums` on number columns; sentence case, no all-caps labels.
- **Columns come from `createDataTableColumnHelper`** and render through `DataTable`; `@tanstack/react-table` is imported here for types only.
- **Phones count.** Every page works at phone width: no horizontal page scroll, tables scroll inside their container.

## API

- **Every API call goes through the generated client in `src/api/generated`** (Orval, from the backend's `openapi.json`): its hooks (`useGetCatalog`, `useListNamespaces`, ...), or its functions inside `useMutation` / `useQuery`. Never edit `src/api/generated`; change the backend DTO or `orval.config.ts` and run `task dev:generate-api`. `apiFetch` adds the `/console/api` prefix and throws `ApiError` (`src/api/apiError.ts`) with FastAPI's `detail`.
- **Model types come from `@/api/generated/model`**, named as the backend DTOs (`CatalogApiResponse`, `CatalogTableApiResponse`, `TableApiResponse`). Where a generated type is looser than the page needs, adapt the component, not the type.
- **Pass names unencoded**; the client encodes path segments and query values. A namespace is `apiNamespace(parts)`, the parts joined by U+001F.
- **Invalidate and remove with the generated `getXQueryKey(...)`.** A key is `[url]` or `[url, params]`, so a list key without params is the prefix of every listing it covers (`getListNamespacesQueryKey(catalog)`: every namespace listing in the catalog); pass `exact: true` for one listing.
- **Tests stub the network through MSW** (`stubCatalogApi`, or `server.use` with the generated `getXMockHandler`), and assert on requests through the stub's call log. Never `vi.stubGlobal("fetch")`.

## Page stories

- **Every page has stories in `src/pages/<Page>.stories.tsx`** (title `Pages/<name>`): `ConsolePage` (`src/stories/`) renders the whole console at a `route`, and the API is answered by `lakehouseHandlers()`, the generated MSW handlers fed from `src/stories/storyData.ts`. A story shows another state by putting handlers in front in `beforeEach` (`getXMockHandler(data)`, `apiError`, `apiPending`). Cover the loaded, empty or error states and phone width (`globals: PHONE` with `expectNoHorizontalPageScroll`).
- Stories run as browser tests with axe (`npm --prefix src/data-platform/frontend run test:stories`, `task -d src/data-platform/frontend component-test`, part of `task gates:pre-pr`); Storybook on port 6007 (`npm --prefix src/data-platform/frontend run storybook`). Its sidebar also shows the design system's Storybook (a ref to port 6006, which must be running; set `DESIGN_SYSTEM_STORYBOOK_URL` to its tailnet URL to browse from another device). Both Storybooks accept `*.ts.net` hosts for `tailscale serve`, and the design system's allows being embedded from another origin.

## Catalog pages

Catalog pages (spec `docs/superpowers/specs/2026-11-07-catalog-context-design.md`) follow one pattern, so every object type looks the same:

- **Every page starts with a header (`PageHeader`, or `TableHeader` on the table page):** `Breadcrumbs` built from `lib/catalogPaths.ts` (Catalogs → catalog → namespace → object), the title, and the object's `ActionsMenu` beside it (Edit / Rename / Delete where Polaris allows them; a table holds Rename and Delete, its properties are edited in its Properties tab; views and generic tables hold Delete only).
- **List pages use `ResourceListPage`** (Catalogs, catalog, namespace, Maintenance policies, Discovery policies): the header, then a list with its New button and per-row delete. Its `notices` prop puts content between the header and the list, one banner per message (the Discovery policies page shows one negative banner per scanned catalog with a current failure); the `errors` prop instead merges load failures into one banner inside the list. **Lists are unframed, like the Tables page:** a table sits on the page under its heading row, never inside a bordered, tinted `Panel`; panels are for summaries and facts, not for wrapping a table. The namespace page lists tables, views and generic tables in one list with a Type column.
- **The Tables page filters by status with `MultiSelect`, kept in the url** (`useTableStatusFilter`): `?status=managed,dropped`; no parameter, or one naming no known status, is the default (managed, unmanaged and undecided, dropped hidden) and the page keeps its url clean there; `?status=` means none selected and shows "No status selected." Changes use `replace` navigation. Filter state a user may share or reload belongs in the url this way.
- **Every delete uses `ConfirmDeleteDialog`:** it names the object and its full path, enables Delete only after the user types the name, and shows Polaris's error (a non-empty catalog or namespace is refused, never cascaded). A page that deletes or renames the object it shows calls `useLeavingPage` so its queries stop before it navigates away.
- **Draft-only deletes skip the dialog:** deleting a row of an unsaved draft (a discovery rule of a discovery policy's draft, before Save) removes it at once; nothing is lost before Save, and Discard changes brings it back. Detaching a policy, maintenance or discovery, is not a delete either and skips `ConfirmDeleteDialog`: it takes the policy off a place, and attaching again puts it back.
- **Discovery policies have three pages** (`lib/discoveryPolicyPaths.ts`): the list `/discovery-policies` (by name, with no default discovery policy among them; New opens `CreateDiscoveryPolicyDialog`, which asks for the first rule, since a policy holds at least one; delete is disabled for an attached policy, and a delete the API still refuses, attached since the list was read, shows its 409 detail in the dialog), the edit page `/discovery-policies/:name` and the read-only version page `/discovery-policies/:name/versions/:version`. `/discovery-rules` redirects to the list, and the sidebar entry is "Discovery policies". A rule is an action, include or exclude, and a table name pattern, read top to bottom, the last match deciding. The edit page holds the rules as a page-level draft with Save and Discard changes (`lib/discoveryPolicyDraft.ts`): `DiscoveryRuleEditor` edits one row per rule in place (its action, its pattern, move and delete), Add rule appends an include rule with an empty pattern and focuses it, and Save stays disabled while the draft has no rule or a rule without a pattern. `DiscoveryRulesTable` shows a version's rules read-only. Actions read "Include" and "Exclude" everywhere, from one shared label helper (`actionLabel`). The version page lists what that version changed against the previous one, worked out in the console from the two versions (`lib/discoveryPolicyChanges.ts`): a rule has no id, so the rules are compared as (action, pattern) pairs along their longest common subsequence, and a changed or moved rule reads as the old one removed and the new one added.
- **A discovery policy is attached and detached on its edit page and on the target pages.** The edit page lists every target it is attached to (`DiscoveryPolicyAttachments`, `AttachDiscoveryPolicyDialog`): the catalog is picked from the catalogs API, the namespace (dot-joined) and the table are typed, and the API's 404, 403 or 422 (a namespace level holding a dot) shows in the dialog. Each attachment row shows its catalog's scan state from `GET /v1/scanned-catalogs` (`lib/catalogScanState.ts`: scanned, not scanned yet, not scanned, or "Cannot access" / "Catalog not found" with the detail). A row is its place, so Detach names it by its type and path (`DELETE …/attachments?target_type=&path=`, the path repeated once per part, `lib/detachPlace.ts`), and rows are keyed by `lib/policyTargetKey.ts` (type, table uuid and path, so an old record and a recreated table of one path stay two rows). **An attachment reads `Orphaned` only when its target no longer exists, not when it is empty**, for discovery and maintenance attachments alike, and a catalog the platform's credential cannot read is not orphaned. After an attach or detach, `invalidateDiscoveryPolicyAttachments` refetches every discovery policy's attachments, the policy list, the scanned catalogs and the table records (`invalidateTableRecords`: every `GET /v1/tables/{uuid}` and table listing, since an attach to a table discovery has not seen registers it undecided).
- **The table page joins two APIs:** the catalog API for the header, the Overview summary and the Schema and Properties tabs, and the maintenance API for the Commits, Maintenance and Reconciliations tabs. A table maintenance does not manage shows `MaintenanceEmptyState` with its reason, through `MaintenanceGate`; `tableMaintenanceState` checks them in this order: no discovery policy in the catalog manages tables (`catalog-not-scanned`, the catalog is missing from `GET /v1/scanned-catalogs`), discovery cannot read the catalog with the platform's credential (`catalog-cannot-access`, a current `cannot_access` failure), discovery has not found the table yet (`not-found`), discovery has not decided it yet (`undecided`, a table a policy was attached to before discovery saw it; after the two catalog reasons, since a catalog discovery cannot read is why a table stays undecided, and before `unmanaged`, which is a decision), no discovery policy that applies manages it (`unmanaged`), and dropped; every reason but dropped links to Discovery policies. The Overview's metrics dashboard (`TableMetricsDashboard`: cards from `GET /v1/tables/{uuid}/metrics/current`, trends from `GET /v1/tables/{uuid}/metrics?range=`) is the same, reading the maintenance API and shown for a managed table only. Its cards are as of the table's last check, which can be an hour behind the header, so they say when they were measured ("Measured 5 min ago", from `observed_at`); its size card is "Data size", data files only, while the header's size also counts delete files. The Overview's Policies panel is the exception, shown for every table: one maintenance has a record of is read by that record's uuid (`GET /v1/tables/{uuid}/effective-policies`), any other by its name (`GET /v1/effective-policies` with `catalog`, `namespace` and `table`), so a policy of either kind can be attached before maintenance manages the table. There is no Policy tab; its old `/policy` URL redirects to the Overview. The header carries only the six catalog numbers, the same for every table; the Overview's Table panel says which discovery policy decided a managed or unmanaged table, from its `decided_by`: "discovery policy `<name>` v`<N>`", linking to that version's page, then "· rule `<position>`" (its position in that version, not the current one) or "· no rule matched"; the name comes from the policy list by `decided_by.policy_id`, and a policy deleted since shows its id in mono with no link. A table whose `decided_by` is null reads "No discovery policy applies"; a dropped table says nothing of it.
- **The table's Schema tab lists every version and compares any two** (`GET …/tables/{table}/schema-versions` and `…/partition-spec-versions`, each with `/{id}/comparison?base=`): the Schema and Partition spec panels each show a `VersionList` (versions named by their Iceberg id, `v0`, `v1`, …, newest first, the newest 10 shown and the rest behind "Show N earlier versions", a neutral `Current` or `Default` badge on the one the table runs, and each version's change summary) beside a `DiffList` of the chosen version against the previous one, or against any other through "Compare with". The page opens on the current version, which is not always the highest id (Iceberg reuses an id). The choice lives in the url (`?schema=&base=&only_changes=1&spec=&spec_base=&spec_only_changes=1`, `replace` navigation); an id the table does not have, which is what an old link carries, shows the current version with a line saying so, never an error, and its comparison is not requested. The DDL panel says it is built from the current schema only.
- **Each commit on the Commits tab links to the schema version it was written with:** the `v<N>` comes from the commits API's `schema_id` and links to the Schema tab at `?schema=<N>` (tooltip "Written with schema vN"); a commit with no `schema_id` (an older format v1 snapshot) shows no link.
- **The table's Properties tab shows every property next to its default** (`GET …/tables/{table}/properties`): every known Iceberg property, every key the table sets and every key its catalog defaults, with the current value, the default and where it comes from (Iceberg, the catalog, or forced by the catalog), a neutral `Modified` or `Custom` badge and a Show modified only switch. A modified, resettable row has Reset (Delete for a custom key with no default), which needs no confirmation; an unset modified row notes that Iceberg's own value applies, and `created-at`, which Polaris writes, gets no badge and no button; Reset all to default confirms in an `AlertDialog` that lists every key it changes. Edit properties (`EditTablePropertiesDialog`) opens from the tab, its only entry point. Every write refetches both the table and its properties.
- **The policy editor keeps each operation's target and options apart** (`OperationPolicySection`): an "In this policy" switch says whether the policy holds the operation (off: the operation is not done on a schedule, its block is `null`; switched on with no target yet, it starts from the platform default's target and options), then a Target group and an Options group; an option left empty means the procedure's default. The cooldowns are not in the editor: they are platform settings, shown read-only on the Platform settings page.
- **Catalog, namespace and table pages show the policy of each kind that applies** (`EffectivePoliciesPanel`, titled `Policies`, one row per entry of the effective-policies answer: `Maintenance`, then `Discovery`): name and version linking to that kind's read-only version page (`/policies/:name/versions/:version`, `/discovery-policies/:name/versions/:version`), a `Dry run` badge on a dry-run maintenance policy, where it comes from (`Attached here`, `From namespace <name>` or `From catalog <name>` linking that page, or `Platform default` for maintenance; `lib/effectivePolicyOrigin.ts`, a table attachment matched by uuid; a discovery entry naming no policy reads "No discovery policy applies", with only `Attach policy`), and `Attach policy` (or `Replace policy` when one is attached here) and `Detach`. **`Detach` shows only on the row attached to this very target**, never for a policy inherited from a parent, and names the entry's `target` by its type and path (a table's path as its record has it, which can trail a rename the page shows). The Maintenance policies page's Attached to column (`PolicyAttachments`) has a `Detach` on every place, orphaned or not (`Detach <policy> from <place>`), since an orphaned place has no page to detach from and an attached policy cannot be deleted. Wherever a detach moves focus afterwards (the next row's Detach, or back to a refused one), an effect keyed on a counter that `onSettled` bumps does it, not one keyed on `isPending` alone: a fast answer can settle with no render seeing it pending. Each button's accessible name starts with its visible label and adds the kind (`Attach policy for maintenance`, `Replace policy for discovery`, `Detach maintenance policy`), so voice control finds it (WCAG 2.5.3). `AttachPolicyDialog` takes the `kind` and lists that kind's policies. After an attach or detach, `invalidatePolicyAttachments` (maintenance: the policy list, the named policies' attachments and the table records) or `invalidateDiscoveryPolicyAttachments` (discovery, see above) runs, and both call `invalidateEffectivePolicies`, which refetches every effective-policies answer, by location and by uuid. A policy save (`PolicyEditor`, `DiscoveryPolicyPage`) calls it too, since the version, the dry-run flag and the description shown in each answer come from the policy.
- **URLs carry names, not ids.** A namespace segment is its parts joined by U+001F and sent as `%1F` (`apiNamespace`), so a part containing a dot round-trips. After every write, failed or not, the page refetches from the API (invalidate in `onSettled`, since a write can fail after part of it landed); it never patches local state.
- **A record opens in a side panel** (Maintenance, Reconciliations, Commits): `Drawer modal={false}` beside the list, full page below 768px. The url names it (`?run=`, `?reconciliation=`, `?snapshot=`, `replace` navigation, through `useOpenRecord`), so a link opens it and the tab's other parameters stay. The panel holds a `DescriptionList` or a `Timeline`, never a table, and reads a record that is not in the list by id (`useGetTableMaintenanceRun`, `useGetTableReconciliation`); a 404 or a 422 shows "This run is no longer available" or "This reconciliation is no longer available" inside the panel (`lib/isGone`), and a record of another table says so. A run read by id is read again on the list's in-flight interval while it, or an attempt of it, is pending, queued, running or waiting to retry (`retry_waiting`; `cancelled` is finished). Only a first read that fails replaces a tab with its error; a background read that fails keeps the list and the open panel and shows an information banner ("Could not refresh. …") until a read succeeds. The Commits panel reads only the loaded history (the commits API has no read by id). The run panel shows the Scope of a compaction ("Whole table" or "Partitions over the target", one line per partition such as `spec 0: region = eu, day(ts) = 2026-11-19`, from the run's `partitions`), its `settings` under Settings, and an attempts timeline.
