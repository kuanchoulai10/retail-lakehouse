# Identity (Keycloak)

Deploys Keycloak 26.8.2 and its PostgreSQL 17.11 database, plus oauth2-proxy v7.15.6, into the `identity` namespace (ambient mesh, gateway routes allowed), and puts a login gate on `platform-gateway`: every gateway path except `/keycloak` (but not its admin console `/keycloak/admin`), `/sso` and `/polaris` needs a Keycloak session. Keycloak is served under `/keycloak` and oauth2-proxy under `/sso`. The realm `retail-lakehouse` is imported at the first start from `keycloak-realm-configmap.yaml`.

## Public origin and issuer

`bootstrap.sh` takes the public origin from `origin::public` (`scripts/utils/origin.sh`: `PUBLIC_ORIGIN` if set, otherwise `https://<tailscale DNS name>:8591`) and writes it to the ConfigMap `public-origin`. Keycloak runs with `KC_HOSTNAME=<origin>/keycloak` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`:

- Tokens and the discovery `issuer` are always `<origin>/keycloak/realms/retail-lakehouse`, whichever URL the request came in on.
- Backchannel endpoints (token, JWKS, userinfo) in the discovery document follow the request, so a pod that asks `http://keycloak.identity.svc.cluster.local:8080/keycloak/realms/retail-lakehouse/.well-known/openid-configuration` gets in-cluster token and JWKS URLs.

`bootstrap.sh` renders the origin into the pod-template annotation `retail-lakehouse.io/public-origin` of the `keycloak` and `oauth2-proxy` Deployments (`envsubst` on `${PUBLIC_ORIGIN}` in the two manifests) and applies them with `kubectl apply`. A changed origin changes the pod template, so both Deployments roll by themselves, also on a rerun after a run that stopped half way; the same origin leaves the pods running. There is no `rollout restart` in the bootstrap.

Other settings: `KC_HTTP_ENABLED=true` (TLS ends at `tailscale serve`), `KC_PROXY_HEADERS=xforwarded`, health and metrics on, `KC_CACHE=local` (one replica), heap `-Xms256m -Xmx512m`.

## Realm `retail-lakehouse`

| Client | Kind | Redirect URIs | Audience mapper |
|--------|------|---------------|-----------------|
| `oauth2-proxy` | confidential, standard flow | `<origin>/sso/callback` | adds `oauth2-proxy` |
| `trino` | confidential, standard flow | `<origin>/oauth2/callback`, `https://localhost:8443/oauth2/callback` | adds `trino` |
| `platform-validate` | confidential, service account only | none | adds `oauth2-proxy` |

The human user `platform-admin` (email `platform-admin@retail-lakehouse.local`, verified, first and last name set, so no required action at first login) has a permanent password. The service account user of `platform-validate` has a verified email `platform-validate@retail-lakehouse.local`. SSO sessions last 12 hours.

The realm JSON references the origin and every secret through Keycloak import placeholders (`${PUBLIC_ORIGIN}`, `${OAUTH2_PROXY_CLIENT_SECRET}`, `${TRINO_CLIENT_SECRET}`, `${PLATFORM_VALIDATE_CLIENT_SECRET}`, `${PLATFORM_ADMIN_PASSWORD}`), filled from the pod environment, so no manifest holds the origin or a secret.

### Realm edits on a running cluster are manual

Keycloak starts with `--import-realm`, which only creates a missing realm (`Realm 'retail-lakehouse' already exists. Import skipped`). Editing `keycloak-realm-configmap.yaml` and rerunning the bootstrap changes nothing in a realm that already exists, and neither does a changed public origin (Keycloak rolls so its hostname follows, but the redirect URIs stay). The bootstrap does not reconcile the realm. Apply such changes by hand in the admin console or with `kcadm.sh`, or re-onboard. For a changed origin follow "Origin changed" below.

## Origin changed

The origin is part of the realm (redirect URIs, web origins), of Keycloak's hostname, of oauth2-proxy's URLs and of Trino's OAuth2 callback. `validate.sh` catches a stale realm: it sends an anonymous auth request for `oauth2-proxy` with `redirect_uri=<origin>/sso/callback` and for `trino` with `<origin>/oauth2/callback`, and Keycloak answers 400 (`Invalid parameter: redirect_uri`) instead of 200 when the realm does not list them. After the origin changes (a new Tailscale name, or `PUBLIC_ORIGIN`), in this order:

1. Rerun this wave, which rewrites the ConfigMap `public-origin` and rolls Keycloak and oauth2-proxy:

   ```bash
   KUBE_CONTEXT=retail-lakehouse bash platform/13-identity/bootstrap.sh
   ```

2. Update the realm. The bootstrap does not do it (the import skips an existing realm). The commands run `kcadm.sh` in the Keycloak pod and log in as the master-realm admin through the pod's `KC_BOOTSTRAP_ADMIN_USERNAME` and `KC_BOOTSTRAP_ADMIN_PASSWORD`, which are `secretKeyRef`s to Secret `keycloak-admin` (keys `username`, `password`), so no credential crosses the command line or the terminal. The values are the ones the realm import sets (`trino`'s web origins were derived from its redirect URIs at import):

   ```bash
   ORIGIN="$(kubectl get configmap public-origin -o jsonpath='{.data.origin}' --namespace identity --context retail-lakehouse)"
   kubectl exec deployment/keycloak --namespace identity --context retail-lakehouse -- \
     env ORIGIN="${ORIGIN}" bash -c '
   set -euo pipefail
   kcadm() { /opt/keycloak/bin/kcadm.sh "$@" --config /tmp/kcadm.config; }
   kcadm config credentials --server http://localhost:8080/keycloak --realm master \
     --user "${KC_BOOTSTRAP_ADMIN_USERNAME}" --password "${KC_BOOTSTRAP_ADMIN_PASSWORD}"
   client_id() {
     kcadm get clients -r retail-lakehouse -q clientId="$1" --fields id --format csv --noquotes
   }
   kcadm update "clients/$(client_id oauth2-proxy)" -r retail-lakehouse \
     -s "redirectUris=[\"${ORIGIN}/sso/callback\"]" \
     -s "webOrigins=[\"${ORIGIN}\"]" \
     -s "attributes.\"post.logout.redirect.uris\"=${ORIGIN}/*"
   kcadm update "clients/$(client_id trino)" -r retail-lakehouse \
     -s "redirectUris=[\"${ORIGIN}/oauth2/callback\",\"https://localhost:8443/oauth2/callback\"]" \
     -s "webOrigins=[\"${ORIGIN}\",\"https://localhost:8443\"]"
   for c in oauth2-proxy trino; do
     kcadm get "clients/$(client_id "$c")" -r retail-lakehouse --fields clientId,redirectUris,webOrigins
   done
   rm -f /tmp/kcadm.config
   '
   ```

   Never print the whole client (`kcadm get clients/<id>` without `--fields`): it includes the client secret.

3. Rerun `23-trino`, which rewrites its ConfigMap `trino-public-origin`; the checksum annotation on Trino's pod templates rolls the coordinator and workers:

   ```bash
   KUBE_CONTEXT=retail-lakehouse bash platform/23-trino/bootstrap.sh
   ```

4. Run the validates (this wave's redirect URI probes, Trino's `/ui/` redirect to `<origin>/oauth2/callback`, and the rest):

   ```bash
   KUBE_CONTEXT=retail-lakehouse bash platform/13-identity/validate.sh
   KUBE_CONTEXT=retail-lakehouse bash platform/23-trino/validate.sh
   task apps:validate KUBE_CONTEXT=retail-lakehouse
   ```

Session cookies issued under the old origin do not reach the new one, so every user logs in again.

```bash
kubectl get secret keycloak-clients \
  -o jsonpath='{.data.platform-admin-password}' \
  --namespace identity \
  --context retail-lakehouse | base64 -d; echo
```

## Validation token

`gateway::token` (`scripts/utils/gateway.sh`) prints a `platform-validate` access token. It reads the client secret from `identity/keycloak-clients` and posts a client credentials grant to `/keycloak/realms/retail-lakehouse/protocol/openid-connect/token` through the gateway (the same port-forward as `gateway::curl`, since the host cannot resolve cluster DNS). It returns 1 when the Secret does not exist.

## Login gate

The gate is the Istio extension provider `oauth2-proxy` (HTTP ext_authz, registered in `platform/12-istiod/values.yaml`) plus the `AuthorizationPolicy` `platform-gateway-sso` in `istio-ingress` (`platform-gateway-sso-policy.yaml`). Envoy in the gateway sends every request (original method and path, headers `cookie`, `authorization`, `x-forwarded-*`) to oauth2-proxy before routing it:

- With a valid session cookie `_oauth2_proxy`, or a valid Keycloak bearer token, oauth2-proxy answers 200 (`static://200`) with `X-Auth-Request-User`, `-Email` and `-Preferred-Username`, which Envoy adds to the upstream request.
- Without either, oauth2-proxy answers 302 straight to the Keycloak login page (`--skip-provider-button`) and sets the CSRF cookie; Envoy passes `location`, `set-cookie` and `content-type` to the browser. After the login Keycloak sends the browser to `<origin>/sso/callback`, oauth2-proxy sets the session cookie and redirects back to the page first asked for, query string included.

Ungated paths (the first rule's `notPaths`): `/keycloak`, `/keycloak/*`, `/sso`, `/sso/*` (the login flow itself) and `/polaris`, `/polaris/*` (an API with its own Polaris tokens; the Polaris console spike sends `Authorization: Bearer <Polaris token>`, which the gate must not see). A second rule gates `/keycloak/admin` and `/keycloak/admin/*` again, so the Keycloak admin console and admin REST API need a platform session on top of Keycloak's own admin login; `/keycloak/realms/...` (login, token, certs, discovery) and `/keycloak/resources/...` stay ungated. The admin console's own bearer token (master realm) fails oauth2-proxy's JWT check, and oauth2-proxy then falls back to the session cookie the browser also sends. Every other path is gated, including `/` and any route added later: a new UI registers nothing. Istio normalizes the path before matching, so `/keycloak/../console/` and `/keycloak/x/../admin/` are gated; Keycloak itself answers 400 to `/keycloak//admin/...`.

The ext_authz call to oauth2-proxy has a 5 s timeout (`timeout: 5s` on the provider in `platform/12-istiod/values.yaml`; Istio's default is 600 s), so a hung oauth2-proxy answers 403 within 5 s instead of holding requests open; a timeout fails closed like any other check failure.

oauth2-proxy answers some paths itself, with 200 and no session, before its auth logic: `/robots.txt` at the root (hard-wired in v7.15.6), the ping and ready paths, and everything under its proxy prefix. An ext_authz 200 means allow, so such a path would reach the upstream behind the gate. Ping and ready are moved under `/sso` (`--ping-path=/sso/ping`, `--ready-path=/sso/ready`), and `/sso` is ungated anyway. `/robots.txt` cannot be moved, so the DENY policy `platform-gateway-sso-builtins` (`platform-gateway-sso-builtins-policy.yaml`) answers it with 403 for everyone. Istio evaluates CUSTOM before DENY. When upgrading oauth2-proxy, check its `buildServeMux` and `buildPreAuthChain` for new root-level handlers; `validate.sh` probes the known ones.

`bootstrap.sh` applies both policies (DENY first) only after the oauth2-proxy rollout succeeds, so a rerun never locks validation out behind a gate with no proxy.

### oauth2-proxy settings

| Setting | Value |
|---------|-------|
| Provider | `keycloak-oidc`, client `oauth2-proxy` (secret `keycloak-clients/oauth2-proxy-client-secret`), scope `openid email profile`, PKCE `S256` |
| Issuer | `<origin>/keycloak/realms/retail-lakehouse` (the public issuer), with `--skip-oidc-discovery` |
| Login URL | `<origin>/keycloak/realms/retail-lakehouse/protocol/openid-connect/auth` (public, the browser follows it) |
| Redeem, JWKS, profile URLs | `http://keycloak.identity.svc.cluster.local:8080/keycloak/realms/retail-lakehouse/protocol/openid-connect/{token,certs,userinfo}` (in-cluster) |
| Redirect URL / proxy prefix | `<origin>/sso/callback` / `/sso` (not `/oauth2`, which Trino's own OAuth2 callback uses); ping and ready paths `/sso/ping`, `/sso/ready` |
| Mode | `--reverse-proxy`, upstream `static://200`, `--set-xauthrequest` |
| Bearer tokens | `--skip-jwt-bearer-tokens`: a Keycloak JWT with the public issuer and audience `oauth2-proxy` (and an email) is accepted instead of a cookie |
| Cookie | `_oauth2_proxy`, `Secure`, `HttpOnly`, `SameSite=Lax`, 12 h (`--cookie-expire=12h`, the same as the realm's SSO session), session stored in the cookie (no Redis), no refresh; secret `oauth2-proxy-cookie/cookie-secret` |
| Users | `--email-domain=*`: every Keycloak user of the realm may pass |
| Memory | request 16Mi, limit 128Mi (see Memory) |

The origin reaches oauth2-proxy as `$(PUBLIC_ORIGIN)` from the ConfigMap `public-origin`; the pod annotation `retail-lakehouse.io/public-origin` rolls oauth2-proxy along with Keycloak when the origin changes. After the 12 hours, or when the cookie is gone, the next page load goes through the login again (a background `fetch` from an open page may fail until it is reloaded).

### Why the routes set `X-Forwarded-Proto: https`

TLS ends at `tailscale serve`; the gateway sees plain HTTP from the port-forward, and Envoy overwrites `X-Forwarded-Proto` with `http`. Keycloak (`KC_PROXY_HEADERS=xforwarded`) then issued its cookies without `Secure` and with `SameSite=Lax` instead of `Secure; SameSite=None`. The `keycloak` and `oauth2-proxy` HTTPRoutes set `X-Forwarded-Proto: https` with a `RequestHeaderModifier`, so both always see the public scheme. No host is set: Keycloak's hostname is fixed and oauth2-proxy's URLs are absolute.

### Fails closed

The ext_authz filter does not allow on failure: with oauth2-proxy down or unreachable every gated path answers 403, and with Keycloak down nobody can log in (existing session cookies keep working until they expire, since oauth2-proxy checks them itself). The ungated paths keep working.

### Trust boundaries

What the gate does not protect yet (follow-ups; none is exploited by a current upstream, since no upstream reads identity headers today):

- **Client-sent `X-Auth-Request-*` headers.** Envoy adds oauth2-proxy's `X-Auth-Request-User`, `-Email` and `-Preferred-Username` on allow, but it does not remove the ones a client sent: they reach the upstream unchanged on the ungated paths (`/keycloak`, `/sso`, `/polaris`), and on gated paths whenever oauth2-proxy omits a claim (a token without `preferred_username`, for example). Strip them at the gateway before any upstream trusts identity headers; this is a precondition for phase 3 (identity-aware upstreams).
- **Post-login redirect host.** `--trusted-proxy-ip` is unset and `x-forwarded-host` is in the ext_authz check headers (`includeRequestHeadersInCheck`), so oauth2-proxy builds the post-login redirect from a client-sent `X-Forwarded-Host`: a client can steer its own redirect to another host. It is kept because the port-forward path relies on it; recorded rather than changed.
- **Keycloak forwarded headers.** `KC_PROXY_HEADERS=xforwarded` makes Keycloak trust `X-Forwarded-*` from any caller that reaches its Service, including every in-cluster pod, not only the gateway.
- **Ungated prefixes are global.** The policy matches paths, not routes: an HTTPRoute from any allowed namespace under `/sso`, `/keycloak` or `/polaris` would be ungated too. Only this wave and `21-polaris` may route there.

## Break-glass

The gate fails closed (see above). To reach a UI while Keycloak or oauth2-proxy is down, skip the gateway and port-forward straight to the UI's Service, for example:

```bash
kubectl port-forward service/temporal-web 8080:8080 --namespace temporal --context retail-lakehouse
```

## Validation

```bash
KUBE_CONTEXT=retail-lakehouse bash platform/13-identity/validate.sh
```

Checks the ambient and gateway labels, the key names of the four Secrets, the `keycloak-db`, `keycloak` and `oauth2-proxy` rollouts, HBONE for every pod, both HTTPRoutes, the discovery `issuer` through the gateway, and that `gateway::token` returns a token whose `iss` is the public issuer and whose `aud` contains `oauth2-proxy`. Then the gate:

- the expected origin is read from the deployed ConfigMap `identity/public-origin` (`gateway::origin`; `origin::public` only while that ConfigMap does not exist), so a validate run never recomputes a different origin than the one deployed;
- `gateway::assert_redirect_uri` sends anonymous auth requests for client `oauth2-proxy` with `redirect_uri=<origin>/sso/callback` and for client `trino` with `<origin>/oauth2/callback` and expects 200; a realm that still lists an old origin answers 400 (see "Origin changed");
- `gateway::curl_anonymous /identity-gate-probe/` gets a 302 to `<origin>/keycloak/realms/retail-lakehouse/protocol/openid-connect/auth`;
- `gateway::curl /identity-gate-probe/` (with the `platform-validate` bearer token) succeeds;
- `gateway::curl_anonymous` on `/keycloak/admin` and `/keycloak/admin/master/console/` gets a 302 to the Keycloak login with `redirect_uri=<origin>/sso/callback` (the admin console is gated), while `/keycloak/realms/retail-lakehouse/.well-known/openid-configuration` stays 200 anonymously;
- `gateway::curl_anonymous /polaris/api/catalog/v1/config` gets Polaris's own 401 (ungated), once the `polaris` HTTPRoute exists (wave 21);
- `gateway::curl_anonymous` on `/robots.txt`, `/robots.txt?x=1`, `/ping` and `/ready` gets 302 or 403, never an oauth2-proxy built-in 200; 404 is accepted only while no HTTPRoute on `platform-gateway` takes `/`.

The gate probe is a second rule of the `oauth2-proxy` HTTPRoute. Envoy answers a path that matches no route with 404 before the ext_authz check, so on a fresh onboard (no UI route before wave 21) a check on `/console/` could not see the gate; the probe path exists from wave 13 on. `task apps:validate` reruns this script after every wave, which also runs the `/polaris` check.

## Validating through the gate

`gateway::curl <path> [curl args]` gets a token with `gateway::token` and sends `Authorization: Bearer <token>` (through a free file descriptor, never on the command line). Wave validate scripts call it unchanged:

- When `identity/keycloak-clients` does not exist (a fresh onboard below wave 13), it sends no header.
- When the Secret exists but no token comes back, it fails with an error instead of calling anonymously.
- When a token was sent but a response redirects to `<origin>/keycloak/realms/retail-lakehouse/protocol/openid-connect/auth`, it fails: the gate rejected the token. Without this, a caller with `curl -fsS -o /dev/null` would accept the 302 as success. The origin comes from `gateway::origin`: the `public-origin` ConfigMap, or `origin::public` while that ConfigMap does not exist (a failed read of the ConfigMap fails the call). `gateway::curl_anonymous <path> [curl args]` is the same call without a token, for checking what an anonymous browser gets.
